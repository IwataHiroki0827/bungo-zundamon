# CHG-F006-003 山月記(000624)の容量actual・atomic受入を実装しT-151を完結する

## 経緯

CHG-F006-002でF006 work-preview構築（段階B2前半）が成功し、残るは容量actual
（FUN-F006-009後半）とatomic受入（FUN-F006-010、`src/content/f006-acceptance.ts`
新設）だった。DD-F006.mdは既にFUN-F006-010へ「方式訂正(2026-08-22)」を記載しており、
汎用`promoteVerifiedWorkArtifacts`（`src/content/batch-acceptance.ts`）が要求する
「voiced stageのoutputHashesへgenerationDigest/completenessDigestを直接含む」契約と、
F006の`scripts/f006-prepare-voice.ts`が採用した間接ハッシュ規約（`voiceEvidenceRef`
ファイルのSHA-256を1件だけ格納）が噛み合わないことを指摘し、F003の
`src/content/f003-review-acceptance.ts`と同型の専用薄いラッパー
`src/content/f006-acceptance.ts`を新設する方針を確定していた。

実装検証の結果、この訂正方針は正しかった一方、当初想定していたv0.5.0
`PublishedBaselineBundle`（`src/content/published-baseline.ts`）の新規mint済み
loaderは**不要**と判明した。`promoteVerifiedWorkArtifacts`のシグネチャ自体が
`publishedInvariant`を引数に取らず（`stagedVoice`/`completeness`/`actual`/`preview`/
`pages`/`contentInvariant`/`distInvariant`のみ）、かつF006のwork-preview構築
（`scripts/f006-content-preview.ts`の`assertV050Invariant`）が既にbuild時点で
F001〜F005 backward-compat検証を完結させているため、acceptance側での重複検証は
設計上不要だった。

## 決定

1. **`scripts/f006-capacity-actual.ts`（新規）**: F002固有の`batch-runtime.ts`
   `executeCapacityActual`は転用せず、既存`baseline.ts`
   （`loadAndVerifyF001Baseline`/`verifyF001Invariant`/`verifyF001DistInvariant`、
   feature非依存のF001 baseline）・`pages-preview.ts`（`buildPagesPreview`、実vite
   build）・`voice/budget.ts`（`measureGitRepository`/`verifyActualCapacity`）を
   直接呼ぶ新規thin scriptとして実装した。間接ハッシュ規約からassertInputs
   要求の直接ハッシュを再導出するため、`transitionWorkState`（同一work statusへの
   再遷移を許さない）を経由せず、`batch-runtime.ts`の`appendActualEvidence`
   （F002固有）と同型の直接manifest操作パターン（`validateBatchManifest`→
   `writeBatchManifestAtomic`）を用いて次の2段階でstageRecordsへ追記した:
   - 2件目のvoiced stage record（work statusはvoicedのまま、outputHashesへ
     `generation.generationDigest`・`completeness.completenessDigest`を直接格納）
   - 容量actual実行後のcapacity-actual stage record（inputHashesへ上記2件の
     直接ハッシュとpreview buildSha256、outputHashesへactual/pages/invariant各
     reportのハッシュを格納）。`src/content/batch.ts`の`validateWorkProgress`が
     定める「status=voicedかつstageRecords末尾がcapacity-actualの場合は直前が
     voicedであること」という既存特例にそのまま適合する。
2. **`src/content/f006-acceptance.ts`（新規）**: `src/content/f004-acceptance.ts`
   と同型のprepare/accept/recover三関数構成。`prepareF006WorkAcceptance`は
   canonical allowlist path（voice-evidence・voice-generation・voice-completeness・
   capacity-actual・work-previewの各cache）から実体を再読込・再検証し、
   `WeakSet`でmint済み値だけを`acceptF006Work`/`recoverF006WorkAcceptance`が
   受理するbranded prepared値を組み立てる。manifest上のcapacity-actual stage
   recordはworkが`accepted`へ進んだ後は`stageRecords`末尾が`accepted`記録に
   変わるため、`findLast(stage === 'capacity-actual')`で名前検索する（`at(-1)`
   固定参照はaccepted後に誤判定するバグを実装中に検出し修正した）。
   `promoteVerifiedWorkArtifacts`・`writeBatchManifestAtomic`（`batch.ts`）は
   無変更のまま呼ぶ。
3. **`scripts/f006-accept-work.ts`（新規）**: 上記2モジュールを呼ぶCLI
   entrypoint。

山月記(000624)に対して実際に`scripts/f006-content-preview.ts`（再実行して
work-preview再構築）→`scripts/f006-capacity-actual.ts`→
`scripts/f006-accept-work.ts 000624`を実行し、容量actual結果`pass`
（reasons: []、freeBytes約41.6GB）、work statusを`voiced → accepted`まで
遷移させ、生成WAV 3件（計404,100 bytes）を`.voice-stage-000624/`から
`content/batches/F006/accepted-audio/000624/`へ正式昇格した。batch全体status
は`draft`のまま（他2作品`pending`のため既存`batchStatusFromWorks`仕様どおり）。
