# CHG-F005-046 write予約前ProcessStart取込fence

## 変更理由

CHG-F005-045のproduction run `31221410484`は`F005_ETW_WRITE_COMPLETION_DRAIN_LATE_DIAG_WRITE_ACTIVE_PRODUCER_RESERVATION_BIRTH_RECORD_MISSING`へ到達した。producerの保持handle・PID/start key/sequenceは`ReserveWrite`で確定できたが、同じgateを待つProcessStart callbackが予約handler時点で未取込だったことを示す。

この状態をlate event認可の根拠にしてはならない。write予約を成功させる前に、保持handleと同じprocess sequenceのProcessStart recordを有限時間だけ待ち、event-time birth QPCを予約QPCより前に確定する。観測不能・tuple不一致・待機中state変化は予約自体をfail-closedにする。

## 変更内容

### 1. 非deadlock待機

`ReserveWrite`は既存のpipe threadが`gate`を保持した状態で呼ばれる。phase/path/pending leaseとproducerの保持handle・PID/start key/sequenceを初期検査した後、`processBirthByPid[producerPid]`に同一sequence recordがなければ、QPC基準10秒deadlineまで`Monitor.Wait(gate, remaining)`する。`Monitor.Wait`がgateを解放している間だけ`ObserveProcessBirth`がmapを更新でき、record追加・更新時は`Monitor.PulseAll(gate)`する。条件確認とwait開始を同一gateで行いlost wakeupを防ぐ。

`etwSession.Flush`をgate保持中に呼ばない。pipe接続、producer handle、初期phase reference/instanceは待機中も保持するが、`pendingWriteLease`はまだ作成せず予約成功を外部へ返さない。timeout、guard poison、journal close、process終了は有限停止する。

Disposeはgate内で`disposed = true`、first failure `CAPACITY_SESSION_ABORTED`、`Monitor.PulseAll(gate)`を順に実行してからcancelする。pipe taskの完了を確認する前にETW session、Job、process handleを破棄しない。wait loopはwakeごとにfailureCode、disposed、cancellation、journalClosedをprocess/map再参照より先に確認する。既存failureCodeがある場合はそのcodeをそのままthrowし、replyとjournal/statusのfirst failureを一致させる。Dispose/cancelでpipe taskが固定上限内に完了しない場合も共有resourceを先に破棄せずabort timeoutへ停止する。

予約transaction自身はwait前にlease、snapshot、semantic/capacity/notice/Observationを変更しない。一方、gate解放中に認可された別ETW callbackが行った正当な更新はrollbackしない。この並行更新を含め、初期phase/path/pending lease等が変化した場合は予約だけをSTATE_CHANGEDで停止する。

### 2. 待機後の再検査と線形化

record観測後も同じgate内でfailure/journal/active phase reference・fields、pending lease/path不存在、保持process PID/start key/sequence・non-signaled・Job membership、birth record sequence・positive QPCを再検査する。

全再検査後に予約QPCを1回だけ取得し、`phaseStartedAtQpc < birthStartedAtQpc <= reservedAtQpc`を確認してから、CHG-F005-045の`ObservedProducerBirthSnapshot`をrecord observed=trueで作成し、`PendingWriteLease`を公開する。待機前のQPCを予約境界に使わない。待機中にmapが同一PIDの別sequenceへ更新された場合はtuple mismatchとして停止する。

deadlineはproduction共有純粋規則で`checked(startQpc + checked(frequency * 10))`を作り、overflow、frequency非正、start非正はSTATE_CHANGEDとする。remainingはwake後にQPCを再取得して`now >= deadline`の場合だけtimeoutとする。QPC tickから`Monitor.Wait`へ渡すmillisecondsは正のremainingをceiling変換し、1ms未満を1ms、`int.MaxValue`超を上限へsaturateする。`Monitor.Wait`のfalseだけでtimeoutを決めず、spurious wakeとdeadline -1/同値/+1を同じloop規則へ戻す。

entry時のbirth record fingerprintをpresent/sequence/started QPCのscalarで凍結する。entry absentまたはentry stale別sequenceはwaitする。currentがexpected sequenceなら成功する。currentがentry fingerprintのまま、またはduplicate pulseなら待機を続ける。absentから別sequenceが出現、またはentry staleから別のmismatch fingerprintへ更新された場合はtuple mismatchとする。

### 3. 固定失敗契約

追加する予約fence raw IPC codeは`WRITE_LEASE_PRODUCER_BIRTH_TIMEOUT`、`WRITE_LEASE_PRODUCER_BIRTH_TUPLE_MISMATCH`、`WRITE_LEASE_PRODUCER_BIRTH_PROCESS_IDENTITY_FAILED`、`WRITE_LEASE_PRODUCER_BIRTH_STATE_CHANGED`の4件とする。bridgeではそれぞれ`F005_` prefix付きの4 exact codeへ写像し、runner/workflow annotationまで伝播する。completion-drain外部43 code集合は不変だが、予約fence外部集合4件を別型として追加する。unknown/extra/128文字はgenericへ畳む。

優先順位は、既存failureCode、disposed/cancel/journal close、deadline timeout、birth fingerprint tuple、待機後state、process inspectionの順とする。既存poisonがある場合は新codeで上書きせず、pipe replyも同じfirst failureを返す。新4codeはいずれもpipe catchの`PoisonLocked`でjournal/statusと一致させる。

## 試験方針

- record既存ならwait 0回、record欠落ならcondition check→Monitor.Wait→callback update/Pulse→再検査の順を固定する。
- 実Task/ManualResetEvent fixtureでwait中にcallbackがgateを取得できること、lost wakeupなし、同一sequenceで成功、別sequenceで停止を確認する。
- timeout同値/直前、spurious wake、poison、journal close、phase置換、pending lease生成、path生成、process signaled/tuple/Job各falseを固定する。
- deadline overflow、frequency/start不正、QPC→ms ceiling・1ms下限・int上限、wait false後のnow -1/同値/+1を純粋規則で固定する。
- entry absent、entry stale mismatch、matching update、wait中different update、duplicate/no-update pulseのfingerprint表を固定する。
- Dispose/cancel fixtureで即時Pulse、waiterのfailure先行確認、pipe task完了後だけresource disposeとなることを確認する。
- wait前後のprocess identity二重検査、birth/phase/reservationの-1/同値/+1、予約QPCがwait後1回だけであることを確認する。
- real outer gate lockを使う実Task fixtureでcallbackがwait中だけgateへ入り、wake後`Monitor.IsEntered`、再帰lock count復元、pre-wait/duplicate/spurious Pulse、全Taskの短い上限内完了を確認する。
- 全失敗で予約transaction由来のpending lease、snapshot、state、candidateが未作成で、並行callbackの正当更新は保持する。raw/bridge/runner/workflowの4 exact mappingと生値非公開を確認する。
- native規則、関連Vitest、typecheck、ESLint、trace_check、再現build 2回、独立受入、同一source SHAのhosted productionを実施する。

## 承認

認可・要求を変更せずwrite予約のfail-closed前提を強化するdesign変更であり、要求承認ゲートは設けない。独立設計レビュー、実装、影響試験、hosted再観測まで`in-review`を維持する。

独立設計レビュー初回はHigh 0 / Medium 4 / Low 1で、Dispose/cancel resource寿命、QPC deadline算術、failure/external mapping優先順位、stale sequence semantics、実Task fixture不足を指摘した。Dispose Pulse→pipe完了→resource破棄、checked deadlineとceil wait、first failure優先、entry/current fingerprint表、real outer gate fixtureとして反映し再レビューする。

修正後の独立設計レビューはHigh 0 / Medium 0 / Low 0でPASSした。初回5指摘がCHG・FD・DD・UT・IT・QTへ整合して反映され、追加の設計ブロッカーがないことを確認した。
