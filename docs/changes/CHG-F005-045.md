# CHG-F005-045 active lease予約時producer birth snapshot診断

## 変更理由

commit `b45db8052da17419a9006c1803ba9a48c1c14f0c`のproduction run `31217391262`はCHG-F005-044のactive directory限定handoffを通過した後、`F005_ETW_WRITE_COMPLETION_DRAIN_LATE_DIAG_WRITE_ACTIVE_PRODUCER_RECORD_MISSING`で安全停止した。active leaseは`ReserveWrite`でproducerの保持process handle、PID、process start key、process sequenceを確定している一方、CHG-F005-043のbirth分類は別のFileIO認可で作成される`registeredWorkerProcesses`だけを参照する。このため、producerが正しくJob内に存在していても、先行FileIO認可の有無によってbirth分類の正本が欠落し得る。

この停止だけからeventを認可してはならない。active leaseの予約処理時に同一gate内で既に観測済みのETW process birth recordをimmutable snapshotへ凍結し、後続のrecord-missing診断をraw値なしの固定分類へ細分化する。このsnapshotはevent-timeで予約QPC以前の全ProcessStart取込完了を保証するものではない。同じgateを待つ遅延ProcessStart callbackは未観測として固定し、認可せずmissing codeで停止する安全側契約とする。

## 変更内容

### 1. 予約時snapshot

`ReserveWrite`は`job.OpenContainedProcess`と`job.ProcessIdentity`でproducer PID/start key/sequenceを確定し、予約QPCを1回だけ取得する。同じgate内で`processBirthByPid[producerPid]`を1回だけ参照し、次をconstructor-onlyの専用`ObservedProducerBirthSnapshot`へscalar copyする。`PendingWriteLease`はget-only propertyとしてこのsnapshotを保持し、mapの`ProcessBirthRecord`参照自体は保持しない。

- birth recordの存在有無
- recordのprocess sequence
- recordのstarted QPC
- 予約時のproducer PID/start key/sequence
- active phase instanceとphase開始QPC
- lease予約QPC

可変mapは予約後の診断で再参照しない。record欠落は「event-timeで存在しない」ではなく「予約handlerがgate内で参照した時点に未観測」として保存し、予約失敗や認可へ変更しない。予約以前QPCのProcessStart callbackがgate待ちの場合もmissingのまま変化させない。recordが存在する場合も`phaseStartedAtQpc < birthStartedAtQpc <= leaseReservedAtQpc`とprocess sequence完全一致を後段の純粋規則で検査し、矛盾を認可根拠にしない。

### 2. record-missingの固定分類

最初にCHG-F005-043の既存classifierを1回だけ評価する。既存registered recordが存在する場合は従来のtuple mismatch、event birth同値以前、event birth後の3結果を一切変更しない。既存classifierがexact `WRITE_ACTIVE_PRODUCER_RECORD_MISSING`を返した場合だけ、active leaseの予約処理時snapshotを第2の純粋classifierへ1回渡し、次の優先順位で4 codeへ排他的に分類して同じthrow位置で停止する。

1. `F005_ETW_WRITE_COMPLETION_DRAIN_LATE_DIAG_WRITE_ACTIVE_PRODUCER_RESERVATION_BIRTH_RECORD_MISSING`
2. `F005_ETW_WRITE_COMPLETION_DRAIN_LATE_DIAG_WRITE_ACTIVE_PRODUCER_RESERVATION_BIRTH_TUPLE_MISMATCH`
3. `F005_ETW_WRITE_COMPLETION_DRAIN_LATE_DIAG_WRITE_ACTIVE_PRODUCER_AT_OR_BEFORE_RESERVATION_BIRTH`
4. `F005_ETW_WRITE_COMPLETION_DRAIN_LATE_DIAG_WRITE_ACTIVE_PRODUCER_AFTER_RESERVATION_BIRTH`

第2 classifierはrecord未観測を最優先し、record観測済みならproducer PID/start key/lease sequence/record sequence/phase instance/phase start/birth/reservationの完全tuple、次にevent/birth境界を評価する。eventが予約後、active lease/phase差、または第2 classifierへ既存registered record存在を渡す矛盾入力は`STATE_CHANGED`へ閉じる。分類後に既存directory認可、completed-write認可、通常callbackへfall-throughしない。selected seal、producer、proof/replay、queue、ledger、semantic map、capacity、notice、Observation、seal/lease stateを変更しない。

### 3. 外部契約

外部exact codeは既存39件へ上記4件を追加して43件とし、native reply、TypeScript bridge、runner、workflow annotationを同じ集合へ同期する。各codeは127文字以下とし、生のpath/QPC/FileObject/identity/process値を公開しない。IPC、容量actual、candidate保存、candidate branch、Pages公開、`public/`、`data/`条件は変更しない。

## 試験方針

- `ReserveWrite`でbirth record 0/1、sequence一致/不一致、phase→birth→reservationの境界-1/同値/+1を固定する。
- constructor-only scalar snapshotとget-only lease propertyをproduction構造試験で固定し、map record参照を保持しないことを確認する。
- snapshot後に`processBirthByPid`を追加・上書き・削除し、PID再利用の別sequence callbackを処理しても分類結果が変わらないことを確認する。予約QPC以前のProcessStart callbackがgate待ちとなるfixtureでは、handler時未観測missingを固定する。
- 既存classifierを先に1回評価し、registered record存在時の既存3結果を維持する。exact record missing時だけ第2 classifierを1回評価し、矛盾入力だけ`STATE_CHANGED`へ停止する。
- snapshot欠落、tuple不一致、event birth同値以前、birth後の4 codeを各1件以上固定し、排他・網羅・127文字上限を確認する。
- PID、start key、lease sequence、record sequence、phase instance、phase start、birth、reservation、event境界の各単独falseを真理値表で固定する。
- 分類後throw、他認可非fall-through、失敗時全state無変更、外部43 code同期を確認する。
- native規則、関連Vitest、typecheck、ESLint、trace_check、再現build 2回、独立受入、同一source SHAのhosted productionを実施する。

## 承認

認可・要求を変更しないdesign変更であり、要求承認ゲートは設けない。独立設計レビュー、実装、影響試験、hosted再観測まで`in-review`を維持する。

独立設計レビュー初回はHigh 0 / Medium 3 / Low 1で、gate待ちProcessStartを含むconsumer処理順race、既存classifierとの順序不整合、4 exact code未定義、immutable型と単独false試験不足を指摘した。これらを予約handler時未観測の安全側契約、legacy→record-missing fallbackの二段順序、4 code全文、constructor-only scalar snapshotと境界fixtureとして反映し、再レビューする。

独立再レビューはHigh 0 / Medium 0 / Low 0でPASSした。gate待ちcallbackの安全側missing、既存3分類不変、fallback 1回、4 exact codeの96/96/94/87文字、scalar snapshot、map変異・PID再利用・全単独false試験、診断後throwと非認可・state不変がFD/DD/UT/IT/QTまで整合していると判定された。
