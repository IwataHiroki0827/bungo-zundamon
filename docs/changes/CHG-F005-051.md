# CHG-F005-051 active-directory候補多重時の既存predicate適格数診断

## 変更理由

CHG-F005-050のhosted productionでは、run `31233688210`がactive-directory候補多重の固定codeへ到達した。現在のcodeはlate candidateが2件以上であることだけを示し、既存active-directory handoff predicateを候補ごとに適用した場合の適格数が0件、1件、複数件のどれかを外部判別できない。

候補順や最新sealを根拠なく選ぶことは認可拡大になるため行わない。既存active-directory handoff predicateから総candidate数条件だけを除いた共有純粋predicateを候補ごとに評価し、その適格数を生値なしの2 bucketへ固定診断する。既存aggregateとproduction不変条件により適格0件は正常構成できないため、0件を外部bucketにせず`STATE_CHANGED`へ閉じる。

completed-no-lease familyは対象外とする。`WRITE_ACTIVE_LEASE_MISSING` aggregate、`broad`、`lateCandidates`の既存保証により全candidateがCHG-F005-047 predicateを満たすため、total 2以上ならeligibleも常に2以上であり、3 bucket化に識別力がない。CHG-F005-049の既存`COMPLETED_NO_LEASE_DIRECTORY_HANDOFF_CANDIDATE_AMBIGUOUS`を非変更で維持する。

## 変更内容

### 1. 既存predicateの共有化

`ActiveDirectoryHandoffCandidateMatches`をproduction共有純粋規則として追加する。この規則はCHG-F005-044の既存`CanHandoffActiveDirectory`から`lateCandidateCount == 1`だけを除いた全predicateを同じ順序・同じ比較で評価する。

既存`CanHandoffActiveDirectory`は、`lateCandidateCount == 1`かつ共有predicateがtrueの場合だけtrueを返す形へ委譲する。これによりcount 1の既存認可結果と評価軸を完全に維持し、診断と認可predicateの二重実装によるdriftを防ぐ。completed-no-lease predicate/methodは変更しない。新規predicateは候補、seal、phase、lease、ledger、proof、queue、generation handle、semantic stateを参照更新せず、渡されたscalarだけを評価する。

### 2. 多重時の適格数固定診断

`lateCandidates` array snapshotとaggregate確定後、既存active-directory cardinality terminalより前に、aggregateがexact post-reservation writeの場合だけ共有predicateをsnapshot各要素へ適用して`eligibleCount`を算出する。total countが2以上かつ対象aggregateの場合、次の2固定codeのいずれかを返す。

- active-directory: `...ACTIVE_DIRECTORY_HANDOFF_ELIGIBLE_EXACT_ONE` / `...ELIGIBLE_AMBIGUOUS`

各code長は75/75文字である。`eligibleCount == 1`をEXACT_ONE、`>= 2`をAMBIGUOUSとする。判定順は、(1) totalまたはeligibleが負値、eligibleがtotal超過ならaggregateにかかわらず既存`STATE_CHANGED`、(2) 対象aggregateかつtotal 2以上でeligible 0ならproduction不変条件違反として`STATE_CHANGED`、(3) 同対象でeligible 1/2以上なら2固定code、(4) 対象外aggregateまたはvalidなtotal 1以下ならnull、とする。加算はcheckedとし、snapshot長を上限にする。

既存`ACTIVE_DIRECTORY_HANDOFF_CANDIDATE_AMBIGUOUS`は外部互換allowlistへ残すが、新sourceのactive-directory多重経路は2 codeへ置換する。completed-no-leaseの既存codeとthrowは非変更である。EXACT_ONEを含む全結果は診断後ただちにthrowし、候補選択やhandoffを行わない。将来の認可変更はhosted証拠と別変更管理・承認なしに行わない。

### 3. 線形化・非公開・非fall-through

snapshot、aggregate、event-global scalar snapshot、候補別共有predicate、eligible count、fixed code、terminal throwまでを同じ`gate` acquisition内で行う。`writeCompletionSeals`を再列挙せず、`Monitor.Wait`/`Monitor.Exit`/再lockを追加しない。event-globalなauthorization、PID、event kind、FileObject binding、active phase/leaseとそのtupleは候補評価前にscalar/referenceとして1回確定し、候補ごとの評価中に別sourceから再取得しない。

2結果と`STATE_CHANGED`すべてからcompleted-write、completed-no-lease、post-request、active-directory、active-producer、known-directory認可、proof admission、replay、capacity、apply、candidate保存へfall-throughしない。files、allocated、deferred、observations、notices、pending lease、peak、free、ledger、queue、generation handle、seal/phase/lease stateを変更しない。

native reply、journal、TypeScript bridge、runner serialization、workflow annotationは固定codeだけを伝播し、total/eligible count、candidate順序、path、QPC、PID、FileObject、identity、sequence、handle、predicate bitsetを含めない。completion-drain 51 codeへ2 codeを追加して53 codeとし、予約fence4 codeは不変とする。unknown、extra suffix、exact 128文字は既存genericへ正規化する。IPC keys、容量、candidate branch、Pages、`public/`、`data/`条件は変更しない。

## 試験方針

- active-directory共有candidate predicateと既存`CanHandoffActiveDirectory`へall-true/各単独falseを投入し、count 1の旧結果が変更前fixtureと完全一致し、count 0/2では認可しないことを確認する。completed-no-lease methodの構造・fixtureは非変更とする。
- total 2以上、eligible 0/1/2/`int.MaxValue`、対象/別aggregate、負値、eligible>totalを固定し、0と矛盾はSTATE_CHANGED、1/2以上はEXACT_ONE/AMBIGUOUS、対象外またはvalid total 1以下はnullへ排他的に分類する。
- late candidate tupleからaggregate、共有predicate、eligible count、fixed codeまでを一気通貫で構成するreachability tableを作り、EXACT_ONEとAMBIGUOUSがproduction相関を満たして到達可能、NONEは正常構成不能であることを固定する。
- candidate集合の順序反転と、適格1件＋不適格複数、適格2件＋不適格候補を確認し、順序非依存かつ生count非公開とする。
- snapshotからterminal throwまで同一gate、再列挙・wait・再lockなし、2 codeとSTATE_CHANGEDから後段非fall-through、semantic fingerprint不変を構造試験とTask/barrier fixtureで固定する。
- sentinel count/path/QPC/PID/FileObject/identity/sequence/handle/predicate bitsetがreply、journal、runner、workflow annotationへ出現しないことを確認する。
- completion-drain 53 code、予約fence4 code、127文字上限、unknown/extra/exact128 generic化をnative/bridge/runner/workflowで同期する。
- native規則、関連Vitest、typecheck、ESLint、trace_check、再現build2回、独立受入、同一source SHAのhosted productionを実施し、candidate branch、Pages、`public/`、`data/`の非変更を確認する。

## 承認

認可・要求・容量を変更しないdesign-level固定診断であり、要求承認ゲートは設けない。独立設計レビュー、実装、影響試験、hosted再観測まで`in-review`を維持する。EXACT_ONEの観測だけでは認可を変更せず、認可変更が必要な場合は別変更管理の承認対象とする。

## 独立設計レビュー

初回レビューは整合性High 1、実現性High 1 / Medium 1 / Low 1、セキュリティHigh 0 / Medium 0 / Low 0であった。completed-no-leaseは対象aggregate時に全candidateが既存predicate適格となり3 bucketが識別力を持たないこと、active-directoryもNONEが正常構成不能であること、人工的なcount入力だけでは到達不能codeを検出できないこと、invalid count判定順が曖昧であることを指摘された。

completed-no-leaseを対象外としてCHG-F005-049を非変更にし、active-directoryもproduction到達可能なEXACT_ONE/AMBIGUOUSの2 codeへ縮小した。eligible 0とinvalid countは優先順位を明示してSTATE_CHANGEDへ閉じ、late tupleからaggregate・共有predicate・eligible count・codeまでの一気通貫reachability fixtureを追加した。修正後の整合性・実現性・セキュリティ再レビューはすべてHigh 0 / Medium 0 / Low 0でPASSした。
