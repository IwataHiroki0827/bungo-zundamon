# CHG-F006-007 CI(pages.yml)で失敗したf006-acceptance.test.tsをフレッシュcheckout非依存に修正する

## 経緯

v0.6.0候補確定・push後、GitHub Actions `pages.yml`のCI(run `32554802155`、
ubuntu-latest)が4件のテスト失敗で赤くなった。うち1件
(`src/content/f006-acceptance.test.ts`)は確実な新規バグと判明し、本CHGで
修正する。残り3件(`batch-catalog.test.ts`・`f005-run-work.test.ts`・
`published-baseline.test.ts`)は調査の結果いずれもF006と無関係の既存事象
と確認し、本CHGでは修正しない。

## 原因

`f006-acceptance.test.ts`の「永続化済みcanonical artifactからprepareし、
accepted workをbrandedに再検証できる」ケースが、`.cache/batch-accept/F006/
001738/content-preview.json`をはじめとする`.cache/`配下(gitignore対象、
CHG-F006-006の記述どおりwork-preview stagingは965ファイル・約294MBの
一時treeでcommit不可能)のローカル専用ファイルへ直接依存していた。開発機
ではT-153実行時の残存物がたまたま存在したためPASSしていたが、CIの
フレッシュcheckoutでは`.cache/`が空でENOENTになる。

## 対応

`f004-acceptance.test.ts`の`fixture()`/`normalizePreviewFixture()`パターン
(一時workspaceへcanonical artifactを複製し、gitignore対象キャッシュだけを
テスト内で小さなfixture treeとして再構築する手法)を踏襲し、
`f006-acceptance.test.ts`を書き換えた。

- 一時workspace(`mkdtemp`)へ、実際にgit管理されているcanonical artifact
  (`content/batches/F006/batch.json`・`voice-evidence/001738.json`・
  `work-artifacts/001738/{voice-generation,voice-completeness}.json`・
  `capacity-actual/001738.json`・`accepted-audio/`配下の実音声55ファイル
  計約17MB×batch全体約19MB)を複製する。
- `.cache/batch-accept/F006/001738/`配下4ファイル(content-preview・
  dist-preview・f001-content-invariant・f001-dist-invariant)は、1ファイル
  だけの小さなfixture treeを新規構築してbuildSha256を再計算し、
  `capacity-actual/001738.json`のcontentBuildSha256/contentStagingSha256と
  `content/batches/F006/batch.json`のcapacity-actual stage record
  inputHashesへ同じ値を伝播させることで、`prepareF006WorkAcceptance`自身の
  tuple一致検証を満たす。
- `.cache/transactions/accepted-audio/F006-001738.json`(idempotent
  再検証journal)は、実開発機に残るjournalの`evidence`(実際に確定した
  acceptedSources/preTreeDigest/postTreeDigest)をそのまま複製しつつ、
  `nextManifestSha256`だけを複製先workspaceの実manifest hashへ再計算する。
  work は既に`accepted`のため`promoteVerifiedWorkArtifacts`の
  `assertInputs`(voiced限定)はスキップされ、journalの`nextManifestSha256`
  が現在のmanifest hashと一致する限り、実accepted-audio treeの
  postTreeDigest照合以外の副作用なく検証を通ることを確認した。

これにより、CI環境でも再現可能な自己完結fixtureとなり、実開発機の
`.cache/`残存物に一切依存しなくなった。他4ケース(mint偽造拒否・work順
違反・allowlist違反・workId形式違反)は`.cache`読込前に失敗するため元の
実workspace参照のまま変更していない。

## 他3件の調査結果

`git log a6566e9..5324a51 -- <file>`(F006リリース関連commit群の範囲)で
確認した結果、以下3ファイルはF006の一連のcommitで一切変更されていない。

- `src/content/batch-catalog.test.ts`: 「F002 clone sourceを拒否し、
  canonical workから非破壊previewを構築する」が
  `PublicIntegrationError: batch catalog fragmentがありません: F005`で失敗。
  CHG-F006-006で既に「F004時代の汎用helper`prepareBatchWorkPreview`が
  F002/F003分のfragmentしか供給しない設計のまま、F005が`published`へ
  遷移した時点(T-073完了)から潜在する既存gap」と特定済み。F006はまだ
  `accepted`のみで`published`ではないためこのhelperの対象にすら含まれず、
  無関係と再確認した。ローカルでも同一エラーで再現する。
- `src/content/f005-run-work.test.ts`:
  「manifest段階証跡を直前outputへ結合してvoicedまで連続遷移する」が
  `BatchOperationError: published以前にpublish項目は指定できません`で
  失敗。テスト自身が実manifest(F005は既に3作品全てaccepted済み)を
  `status: draft`へ巻き戻して検証用fixtureを組み立てるが、F005の実
  batch.jsonがrelease進行に伴い新たに獲得したbatch level fieldをテストの
  巻き戻しロジックが想定しておらず、`validateBatchManifest`が不整合と
  判定する。F005の実運用状態の進行に追随できていない既存テストの脆さで
  あり、F006とは無関係。ローカルでも同一エラーで再現する。
  (同ファイルの`it.runIf(process.platform === 'win32')`ゲート付きテスト
  1件はローカルWindows機で`.cache/dotnet-f005/publish/f005-guard.exe`
  未ビルドによりENOENTで別途失敗するが、Linux CIではこのit自体が
  実行されないため無関係。)
- `src/content/published-baseline.test.ts`: CIでは`Test timed out in
  5000ms`。単体実行では4件全PASS(実測13〜14秒、既定timeoutより長いが
  単体では問題なし)。フルスイート並列実行下でのみ再現し、同じセッション
  内で`baseline.test.ts`・`batch-runtime.test.ts`・
  `data-integrity.integration.test.ts`・`f003-catalog.test.ts`も同種の
  timeoutを起こすことを確認した。CPU/IO競合によるWindows並列flakyと同型
  の症状であり、CI(共有ubuntu-latestランナー)でも同種のresource
  contentionが起きたものと判断する。決定論的なロジック不備の証跡はない。

いずれもF006の変更範囲外・大規模な影響範囲を持つため、本CHGでは修正せず
報告に留める。CI再実行で解消しない場合は、batch-catalog.test.tsの
F005 fragment gapとf005-run-work.test.tsの巻き戻しロジック更新は個別の
実装タスクとして切り出すことを推奨する。published-baseline.test.ts等の
timeoutは、CI専用のtimeout延長またはtest並列度の調整で緩和できる可能性
がある。

## 検証結果

- `npx vitest run src/content/f006-acceptance.test.ts`: 5件全PASS(修正前は
  1件が`ENOENT`で失敗)
- `npm run lint`: PASS(差分0)
- `npm run typecheck`: PASS(差分0)
- `npm test`(フルスイート1375件): 35 failed。個別再実行で
  `f006-acceptance.test.ts`は全PASSを再確認した。残り34件は上記3ファイル
  (無関係な既存事象)と、F006と無関係のWindows専用native guard binary
  未ビルド(`f005-source.test.ts`・`f005-native-guard.test.ts`・
  `f005-guard-native.test.ts`・`f005-hosted-native-probe.test.ts`、
  `it.runIf(process.platform === 'win32')`によりLinux CIでは実行対象外)・
  frozen historical commit fixtureの非canonical(`f005-catalog.test.ts`、
  CHG-F006-006で既報告の既知事象と同型)・Windows並列resource contention
  (`baseline.test.ts`・`batch-runtime.test.ts`・
  `data-integrity.integration.test.ts`・`f003-catalog.test.ts`)であり、
  いずれも本CHGの変更範囲外。
- Linux環境相当での実行は本タスクでは未実施(Docker等未使用)。
  gitignore(`.cache/`)とCI checkoutの実態(フレッシュworking tree)から
  コード上の根拠で原因を特定した。

複製のみで容量へ影響しない。
