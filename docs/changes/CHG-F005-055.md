# CHG-F005-055 T-109決定的hosted相関検証

## 変更理由

Q-044で、後続fail-closed guardを含む現行Program pinによるT-109 follow-up productionを3 attempt実行しても、前段の既知固定codeで安全停止し、pendingなしbound-directory writeとunbound leaseの固定14 stageへ到達しなかった。productionの自然なETW配送順へ追加で依存する方法では、認可条件を変えずにT-109のhosted影響を有限回で確認できない。

回答「決定的なhosted影響確認方法を別変更管理で設計」を、T-109の認可、lease binding、capacity actual、semantic state、候補保存、公開条件を変更しない範囲へ限定して反映する。同じproduction assemblyの既存診断規則を直接実行するread-only hosted相関試験により、T-109だけを決定的に再試験する。

## 変更内容

### 1. production共有規則を使うT-109 target suite

`native/f005-guard-tests/F005Guard.CorrelationTests.csproj`からProjectReference生成されたproduction assemblyを読み込み、target `CHG-F005-035/T-109`を追加する。規則の複製、test-only production分岐、条件付きコンパイル、guardのIPC operation・環境変数・command line入口追加は禁止する。

privateな`SystemBoundFileObjectNoPendingUnboundLeaseDiagnosticStage`の本体を、production-owned internal `SystemBoundFileObjectNoPendingUnboundLeaseDiagnosticEvaluator.Evaluate`へ抽出する。evaluatorはcurrent inspection、deferred collectionの0/1/複数判定、deferred tuple・identity再照合、retained processのidentity→wait→alive時Job照会と最終stage決定を所有する。production stageはproduction実体のlease/phase/deferred collection、`TryInspect`、`JobObject.InspectRetainedProcess`を渡してevaluatorをexact 1回だけ呼び、その戻り値を加工せず返す。既存認可経路はevaluatorの戻り値を引き続き全てfail-closedとして扱う。

targetは同じevaluatorへ、RUNNER_TEMPの実directory/file、実retained process handle、private Job、production-owned inspection adapterを渡す。PASS markerのactualはevaluatorの戻り値からだけ生成し、target側の期待値、caller供給boolean、偽identity、偽process結果をactualへ変換しない。inspection失敗の負例だけはproduction evaluatorが呼ぶ固定throw adapterで起こし、正常・signaled・世代差・Job外・identity差替えは実Windows APIの結果を必須とする。production stageとtargetの双方が同じevaluatorを呼び、production stage内に旧判定・別`Classify`・後段fall-throughが残らないことをmethod閉包で固定する。

evaluator内部では次のproduction-owned規則を使用する。

- `SystemBoundFileObjectNoPendingUnboundLeaseDiagnosticRules.IsEventAfterReservation`
- `SystemBoundFileObjectNoPendingUnboundLeaseDiagnosticRules.IsDeferredTimestampCandidate`
- `SystemBoundFileObjectNoPendingUnboundLeaseDiagnosticRules.DeferredTupleMatches`
- `SystemBoundFileObjectNoPendingUnboundLeaseDiagnosticRules.Classify`

固定manifestは、予約QPC同値拒否と+1 tick許可、deferred 0件・exact 1件・複数件、deferred QPCの予約同値・予約+1・event同値・event+1、deferred完全tupleの各単独不一致、FileObject zero/bound、14 stageの評価順と先行code優先を個別caseにする。14 stageは`UNBOUND_SNAPSHOT_PRESENT`、`UNBOUND_BEFORE_RESERVATION`、`UNBOUND_CURRENT_INSPECTION_FAILED`、`UNBOUND_CURRENT_MISSING`、`UNBOUND_DEFERRED_MISSING`、`UNBOUND_DEFERRED_TUPLE`、`UNBOUND_CURRENT_ID_MISMATCH`、`UNBOUND_PROCESS_WAIT_FAILED`、`UNBOUND_JOB_QUERY_FAILED`、`UNBOUND_PROCESS_IDENTITY_FAILED`、`UNBOUND_PROCESS_TUPLE`、`UNBOUND_PROCESS_SIGNALED`、`UNBOUND_LEASE_ESCAPE`、`UNBOUND_CANDIDATE`のexact集合とする。

既存T-110 targetのproduction-owned `JobObject`実fixtureを再利用し、RUNNER_TEMPのGUID付きworkspace外rootで実directory/file identityと保持processを生成する。alive private Job member、signaled、PID/start key/sequence差、Job外、identity差替えを実Windows APIで検証する。production evaluatorがcurrent inspection、deferred件数・tuple、identity、retained process inspection、`Classify`を既存順でexact 1回ずつ使用し、T-109以外の認可経路へfall-throughしないことをmethod閉包の構造検査で固定する。

### 2. read-only hosted evidence契約

既存`native/f005-guard-tests/hosted-target-selector.json`へT-109の固定manifestとtest sourceを結合し、今回の`.github/workflows/f005-hosted-native-probe.yml` self-pathではT-109だけを選択する。T-110 57 case、T-122 43 case、T-112 targetと通常native suiteのlocal無縮退試験を維持する。workflow全体の`actions: read`/`contents: read`、checkout credentialなし、push・artifact uploadなし、RUNNER_TEMP raw stdout/stderr各65,536 bytes上限、未知・重複・欠落marker拒否を維持する。

canonical evidenceはCHG-F005-053/054と同じexact key集合を縮退なく再利用する。`schemaVersion`、`kind`、target ID、source commit、workflow run ID/attempt、runner OS/arch・image・Windows build/UBR・PowerShell、Program/project/build.ps1/global.json/workflow/test project/test harness/target source/selector/manifest SHA、pinned native binary SHA、実load production/test assembly SHA・MVID、test executable SHA、固定SDK/runtime、kernel ETW preflight、期待件数・PASS件数、同一head SHAのPages run/attempt/conclusion、deploy job conclusion、top-level `result: pass`だけを含める。path、PID、QPC、FileObject、volume/file identity、process key/sequence、handle、Win32番号、stack、自由文は含めない。既存keyの削除・改名・型変更・任意化を禁止し、T-109固有値は既存target ID・kind・target source・manifest fieldの値だけで表現する。

固定`pages.yml`、`event=push`、同一head SHAのexact 1 terminal run/attemptとdeploy exact 1件`skipped`をbounded pollする。欠落、多重active attempt、timeout、head差、deploy job欠落・異常は固定codeでFAILする。対象試験前後のtracked `public/`・`data/`・candidate/audio/staging差分0とcandidate branch不存在を確認し、既存production candidate workflow、候補保存、Pages、tag、release経路は変更しない。

### 3. T-109 hosted影響判定

次の全条件を満たす単一source commitのcanonical evidenceでT-109のhosted影響をPASSとする。

1. pinned native guard buildとkernel ETW preflightがPASSする。
2. 固定manifest SHA、期待件数、PASS件数が一致し、実load production/test assembly SHA・MVIDをsource/build/runner tupleへ結合する。
3. deferred 0件・exact 1件・複数件、QPC全境界、deferred完全tupleの各単独不一致、14 stage、実process・Job・identity異常が同一production evaluatorの期待結果へ排他的に収束する。
4. production stageとtargetが同じproduction evaluatorを実行し、実fixture結果から最終stageまでを同じ結線で通す。test-only入口、caller供給actual、認可変更、後段fall-throughが存在しない。
5. T-110/T-122/T-112 targetと通常native suiteがlocalで無縮退し、T-109 target追加によって既存selector、manifest、evidence schemaを緩和しない。
6. raw値非公開、semantic state非変更、`public/`・`data/`差分0、candidate branch不存在、同一source SHAのPages deploy `skipped`、verification write権限なしを確認する。

この証跡はT-109固定診断のhosted影響確認にだけ使用する。通常production pipelineのend-to-end成功、候補受入、capacity actual、公開判定の代用にはしない。実productionで対象stageへ自然到達した場合は追加証拠として採用できるが、PASS条件には要求しない。

## 試験方針

- manifestのcase ID、順序、件数、SHAを固定し、欠落・余分・重複・順序差・偽PASS markerを拒否する。
- deferred 0件・exact 1件・複数件、QPC境界、deferred完全tuple、14 stage、先行code優先をproduction evaluatorへ直接投入する。
- 実directory/file identityとprivate Job childを用い、alive memberだけを候補とし、signaled、世代差、Job外、identity差替えを固定拒否へ分類する。
- production method閉包、外部固定code、raw非公開、read-only権限、candidate/Pages非公開を検査する。
- 通常native suite、T-110/T-122/T-112/T-109 target、関連Vitest、typecheck、ESLint、trace_check、同一SHA再現build 2回、独立受入後にhosted targetを実施する。

## 承認

既承認の要求・認可・lease binding・capacity・semantic state・候補保存・公開条件を変更せず、hosted影響確認の試験方法だけを決定化するdesign-level変更である。要求承認ゲートは設けず、独立レビュー、T-129実装、local/hosted影響試験完了まで`in-review`を維持する。

## 独立設計レビュー

初回レビューはHigh 1 / Medium 2 / Low 0であった。純粋な`Classify`と構造検査だけではprivate production stageの実I/O・process結果取込を証明できない点、canonical evidenceのexact key不足、deferred 0/1/複数件の境界不足を検出した。production stageとtargetが共有するproduction-owned evaluator、実fixtureから最終stageまでの同一結線、CHG-F005-053/054と同じexact key集合、deferred cardinality caseを追加した。

別観点レビューのMedium 1件として、target source/manifest、selector、workflow、関連構造試験が影響範囲に明記されていない点も反映した。再レビューではcanonical evidenceのtop-level `result`欠落をMedium 1件として検出して是正した。影響文書レビューのMedium 2件として、DES-F005-012のrelease/公開非流用境界と、DD-F005のtarget ID・test assembly MVID exact keyを補った。最終再レビューはHigh 0 / Medium 0 / Low 0でPASSし、T-129を実装可能とする。
