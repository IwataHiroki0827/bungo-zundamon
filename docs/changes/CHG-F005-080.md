# CHG-F005-080 E2E全滅(net::ERR_ABORTED)の原因調査

## 症状

T-074でF005候補distに対し`npx playwright test`(6ブラウザprojects、144件)を実行したところ、
ほぼ全件が「作品を読み込めませんでした」表示でタイムアウト失敗した。
`content/catalog.json`へのfetchが`requestfailed`イベントで`net::ERR_ABORTED`となっていた。
F005を一切含まない`npm run build`のみのdistでも同一現象が再現し、F005固有の回帰ではないと判明した。

## 調査手順と結果

1. `npm run build`→`vite preview --host 127.0.0.1 --strictPort --port 4187`で起動し、
   `curl`と`node`のnative `fetch`で直接`content/catalog.json`を取得 → 両方とも
   200・1,340,564バイト全量を正常取得。生HTTPレベルでは問題なし。
2. `PLAYWRIGHT_DIST_ROOT=dist`で既存previewサーバに対しPlaywright単体spec
   (`tests/e2e/favorites.spec.ts`)を実行 → 同一症状を再現。
3. 失敗したtraceを展開し `0-trace.network` を確認したところ、
   `content/catalog.json`のresponseに`"_failureText":"net::ERR_ABORTED"`が記録されていた。
   同じrunで`content/licenses.json`・`content/artwork-provenance.json`は正常に200完了していた。
4. `src/main.ts`の`startBungoZundamon`を確認。`catalogLoader`と`noticeLoader`
   (`loadReleaseNoticeBundle`)を共有の`AbortController`で`Promise.all`しており、
   どちらかが reject すると catch節で`abort.abort()`し、もう一方の in-flight fetch を
   キャンセルする実装になっている。
5. `src/notices/release-notices.ts`の`validateReleaseNotices`は
   `manifest.terms.validUntil`と実行時の`now`(`new Date()`)を比較し、
   `nowTime > validUntil`なら`terms-expired` issueを積んで検証失敗にする。
6. `content/licenses.json`(dist/public/contentへ複製されるsource)の値を確認。

   ```json
   "terms": {
     "checkedAt": "2026-07-18T07:25:00Z",
     "validUntil": "2026-08-18T07:25:00Z"
   }
   ```

   一方、実行環境の実時計は2026-08-20〜21であり、`validUntil`を2〜3日超過していた。
7. 仮説検証として、Playwrightの`page.clock.install({ time: new Date('2026-08-10T00:00:00Z') })`
   で有効期間内の時刻へ固定した状態で同じdistへ`#/authors/miyazawa-zunji`へ遷移する
   1件だけのspecを実行 → `.page`が正常に表示され成功した。実時計のままだと失敗する。

## 追加調査: 既に承認・main適用済みの修正が本ブランチに未反映

`queue.yaml`のQ-049/Q-050を確認したところ、この`terms.validUntil`期限判定は
**CHG-F002-005（Q-049承認、期限の概念そのものを廃止する）として既に設計決定済み**であり、
mainブランチではPR #3（`fix/v0.4.1-license-recheck`、CHG-F002-006、commit `957855c`でマージ済み、
v0.4.1として本番デプロイ済み）で`src/notices/release-notices.ts`と`src/notices/credits.ts`の
両方から期限切れ判定(`terms-expired`系issue)を削除済みだった。

一方、feature/F005ブランチ自身のcommit `8c0e320`（同じくCHG-F002-005として実装）は
**`src/notices/credits.ts`のみ修正し、`src/notices/release-notices.ts`は未修正のまま**だった。
`git diff origin/main -- src/notices/release-notices.ts`を実行すると、
本ブランチにだけ以下のブロックが残存していることが確認できる（このブロックがまさに
今回のE2E全滅を引き起こしている`terms-expired`判定そのもの）。

```diff
+  const checkedAt = validInstant(manifest.terms?.checkedAt ?? '');
+  const validUntil = validInstant(manifest.terms?.validUntil ?? '');
+  if (checkedAt === null) addIssue(issues, 'terms-checked-at-invalid', ...);
+  if (validUntil === null) addIssue(issues, 'terms-valid-until-invalid', ...);
+  if (checkedAt !== null && validUntil !== null && checkedAt > validUntil) {
+    addIssue(issues, 'terms-period-invalid', ...);
+  }
+  if (checkedAt !== null && Number.isFinite(nowTime) && checkedAt > nowTime) {
+    addIssue(issues, 'terms-checked-at-future', ...);
+  }
+  if (validUntil !== null && Number.isFinite(nowTime) && nowTime > validUntil) {
+    addIssue(issues, 'terms-expired', ...);
+  }
```

`queue.yaml`のQ-050 `processed_note`にも「feature/F005ブランチには同種の実装が
既に2026-08-19付コミット8c0e320として別途存在しており、F005が将来mainへマージされる際に
軽微なコンフリクト解消が必要になる見込み」と事前に記録されていた。今回発生したのは
まさにその「軽微なコンフリクト」に相当する箇所の実装漏れであり、mainのfix適用時に
`release-notices.ts`側が取りこぼされたケースである。

## 原因の特定結果

**製品コードの意図した仕様通りの動作であり、Playwright/Vite/ローカル環境固有のバグではない。**
さらに、この挙動は既にオーナー承認済み（Q-049/CHG-F002-005）かつmainへマージ・本番デプロイ済み
（v0.4.1、CHG-F002-006/PR #3）の修正によって解消されるべきものであり、
feature/F005ブランチだけがこの修正を`release-notices.ts`に反映し忘れている状態である。

- `content/licenses.json`の権利確認有効期限(`terms.validUntil`)が実行時点の実時計を
  過ぎていたため、`validateReleaseNotices`が`terms-expired`で検証失敗し、
  `loadReleaseNoticeBundle`が例外を投げた。
- `startBungoZundamon`は`catalogLoader`と`noticeLoader`を同じ`AbortSignal`で
  `Promise.all`しているため、noticeLoader側が先に例外を投げると、
  まだstreaming中だった`catalog.json`のfetchも`abort.abort()`で巻き込まれてキャンセルされ、
  Playwrightのnetwork traceには`net::ERR_ABORTED`として記録される。
  UI側は`renderLoadError`で汎用の「作品を読み込めませんでした」画面を表示する。
- これはネットワーク層・配信層(vite preview / Playwright設定)の不具合ではなく、
  「規約再確認の有効期間(`checkedAt`〜`validUntil`)を過ぎたら公開UIをブロックする」
  という意図された安全装置が、実時計の経過によって発火したものである。

## 修正について

`playwright.config.ts` / `vite.config.ts` に不備は見つからなかったため、
指示書の制約に従い設定変更は行っていない。
`content/licenses.json`の`terms.checkedAt`/`terms.validUntil`を書き換えることは
実際に規約(https://zunko.jp/guideline.html)を再確認した事実を伴わない限り行うべきでない
(法的な確認記録の偽装になる)ため、本調査では未修正のまま報告する。

`src/notices/release-notices.ts`自体の修正（`terms-expired`系issueの削除）は
本タスクの指示書が定める「本番コード(`src/`)の広範な変更はしない」の範囲外と判断し、
本調査では実施していない。ただし、この修正は既にオーナー承認・main適用・本番デプロイ済みの
決定であるため、通常のスコープ判断（設計判断が必要な曖昧さ）には該当しない
（曖昧さはなく、単純にfeature/F005ブランチへの反映漏れ）。次のアクションとして
別タスクで`origin/main`の`src/notices/release-notices.ts`をfeature/F005へ反映することを推奨する。

## 影響範囲

- コード変更なし(調査のみ)。診断用に追加した一時spec (`tests/e2e/clock-check.spec.ts`) は
  検証後に削除済み。

## 次のアクション提案

- **最優先**: `origin/main`の`src/notices/release-notices.ts`（`terms-expired`系issue削除済み、
  commit `957855c`/PR #3相当）をfeature/F005ブランチへ反映する。方法は
  (a) mainをfeature/F005へmerge/rebase、(b) 当該ファイルのみcherry-pick、のいずれか。
  `queue.yaml`のQ-050で事前に「軽微なコンフリクト解消が必要」と記録されていた箇所そのものであり、
  設計判断ではなくmain採用済み決定の反映漏れ解消である。反映後に`npm run test:e2e`を
  実時計のまま再実行し、E2E全件が正常完了することを確認する。
- 有効期限切れが「E2E全滅」という分かりにくい形(`net::ERR_ABORTED`)で現れたのは、
  `startBungoZundamon`が`catalogLoader`と`noticeLoader`を共有`AbortController`で
  `Promise.all`しているため。上記のrelease-notices.ts反映で根本原因は解消するが、
  仮に将来別の理由でnoticeLoaderが失敗した場合も同様に分かりにくいabortになるため、
  失敗理由をUIまたはconsoleへ明示する改善は別途検討の余地がある(設計判断が要るため本タスクでは未実施)。
- GitHub Actions上で`test:e2e`を定期実行するworkflowがあれば、この種の反映漏れ・期限切れを
  リリース前に自動検知できる。現状`pages.yml`はE2Eを含んでいない。
