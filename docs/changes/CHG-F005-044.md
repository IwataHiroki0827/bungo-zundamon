# CHG-F005-044 post-reservation parent writeのactive directory認可引き渡し

## 変更理由

CHG-F005-043/T-117のhosted 3 attemptは、対象`WRITE_AT_OR_BEFORE_ACTIVE_RESERVATION`へ未到達だった。attempt 2 run `31213980538`とattempt 3 run `31214432937`は、いずれも`F005_ETW_WRITE_COMPLETION_DRAIN_LATE_RETAINED_PARENT_OTHER_ACTIVE_SAME_PARENT_POST_RESERVATION_WRITE`で安全停止した。

このcodeは、`CompletedRetained`旧sealのparent pathに対するSystem write、unbound FileObject、同じparentを使う別active lease、event QPCがactive lease予約後という完全条件を示す。時系列上は旧sealへ遅延帰属させるより、現在active leaseのdirectory write候補として既存のbound-lease/after-lease認可で再判定すべきである。ただしcompletion drainが先行throwするため既存認可へ到達できない。旧sealで認可せず、単一exact候補だけを既存active directory認可へ専用引き渡しする。

## 予定変更

### 1. 専用handoffの完全条件

`TryAuthorizeWriteCompletionDrainEventLocked`のepoch 0で、次の全条件を満たす場合だけ`activeDirectoryHandoff`を返す。

- late candidateがexact 1件で、aggregate codeが`...POST_RESERVATION_WRITE`である。
- authorization failureが`BIRTH_MISSING`、System PID 0/4、eventがwrite、FileObjectが非0かつledger上unboundである。
- sealは`CompletedRetained`、同一active voice phase、event pathはseal parentである。
- active leaseが存在しseal leaseとは別参照、active phaseとphase instance一致、active lease current pathのparentがevent pathと一致する。
- `eventQpc > activeLease.CurrentPathReservedAtQpc`である。

候補0/複数、setinfo、current path、他bucket、別parent、同一lease、予約同値以前、bound FileObjectは引き渡さず既存codeで停止する。handoffは通常`completionDrainSeal`、T-115 `completedWriteHandoff`、T-116 replay markerとは別の排他的contextとする。

### 2. 引き渡し先の限定

`ObserveEtw`はhandoff時だけ、既存の次の2認可を現行順で評価する。

1. `TryAuthorizeBoundLeaseDirectoryWriteLocked`
2. `TryAuthorizeAfterLeaseReservationDirectoryWriteLocked`

各認可がfalseを返した直後に`failureCode`を確認し、poison済みなら次認可を評価せずそのcodeでreturnする。どちらかがPASSした場合だけ、その既存context、active lease producer PID/sequence、identity/process再検査、normal callback適用へ進む。両方がfalseかつどちらもpoisonしていない場合は`F005_ETW_WRITE_COMPLETION_DRAIN_STATE_CHANGED`で停止する。reserved/completed SetInfo、known no-lease directory、その他の認可へfall-throughしない。

handoff後も`completionDrainSeal == null`とし、旧sealの`SealedParent` proof、sealed recheck/reorder/replay、EventCount更新は行わない。通常のledger `OtherBound` proofを必須とする。`ApplyCallbackSnapshotCoreLocked`は現状、`BindingProof is null`の場合だけdirectory context固有recheckを呼ぶため、handoffのproof-present snapshotではTOCTOU再検査が省略され得る。本変更ではOtherBound retained identity再inspection後、BindingProofの有無にかかわらず、存在する`BoundLeaseDirectoryRejoinContext`または`AfterLeaseDirectoryRejoinContext`のtuple/process再検査をatomic容量適用前に全実行する。両context同時存在は`STATE_CHANGED`で拒否し、proofとcontextの片方だけの検証に縮退させない。

### 3. 認可集合と外部契約

追加認可集合は、単一旧seal late候補の診断条件と、既存active directory認可の完全条件の交差だけである。旧sealだけを根拠に認可せず、active directory認可が拒否した場合は必ず停止する。

外部39 code、IPC、生のpath/QPC/FileObject/identity/process値非公開、容量actual、candidate保存、Pages公開、`public/`、`data/`条件は変更しない。

## 試験方針

- candidate 0/1/2、aggregate exact/他bucket、System PID、write/setinfo、FileObject 0/nonzero・unbound/boundを固定する。
- seal state、active phase参照、parent/current、active lease有無・同一/別、phase instance、same/different parent、event/reservation同値・+1を各falseで固定する。
- handoff、completed-write、post-request replay、normal epochが排他的であることを確認する。
- handoff時だけbound-lease→failureCode確認→after-lease→failureCode確認の順で各1回以下評価し、前者PASS、前者false/後者PASS、両false、前者poison、後者poisonを固定する。
- PASS後のproducer/context、通常`OtherBound` proof 1件、SealSequence null、旧seal proof/recheck/replay/EventCount 0件を固定する。
- proof-present時もretained OtherBound identity→context排他→bound tuple/processまたはafter tuple/process→capacityの順に全再検査する。BindingProof null/non-null、context各単独/両方、全拒否軸、後半失敗時の全state無変更を固定する。
- 引き渡し先の既存cheap/tuple/process/recheck全拒否軸、失敗時全state無変更、39 code非変更を確認する。
- native規則、関連Vitest、typecheck、ESLint、trace_check、再現build 2回、独立受入、同一source SHAのhosted productionを実施する。

## 承認

既存active directory認可との交差だけを追加するdesign変更であり、要求承認ゲートは設けない。独立設計レビュー、実装、影響試験、hosted再観測まで`in-review`を維持する。

独立設計レビューは初回High 0 / Medium 1 / Low 0で、OtherBound proof非null時にcontext固有TOCTOU再検査が省略され得る点を指摘した。proof retained identity後にBindingProofの有無へ依存せずcontext排他とbound/after固有tuple/process全再検査をcapacity前に必須化し、再レビューはHigh 0 / Medium 0 / Low 0でPASSした。exact単一handoff、poison後停止、旧seal非関与、39 code不変が妥当と判定された。

## 実装結果

単一exact `POST_RESERVATION_WRITE`だけを選ぶ純粋規則と排他的`activeDirectoryHandoff`を実装し、handoff時はbound-lease認可、poison確認、after-lease認可、poison確認以外へfall-throughしない構造にした。PASS後は通常`OtherBound` proof、SealSequence null、normal epochを維持し、旧sealのproof・recheck・replay・EventCountへ関与しない。

適用時はOtherBound retained identity再inspection後、BindingProofの有無に依存せずcontext排他、after tuple/processまたはbound tuple/processをcapacity計算前に再検査する。after process再検査はPreflightとApplyで共通helperを使用し、PID、start key、sequence、signaled、Job membershipとinspection例外codeを同じ判定へ固定した。独立受入の初回Medium指摘を受け、`PreflightImmutableRejoinLocked`でも両context排他を個別tuple/processより先行させ、Apply経路と同じSTATE_CHANGED停止に統一した。

ローカル検証はnative規則593件、関連Vitest 5 files / 128件、typecheck、ESLint、trace_check、再現build 2回をPASSした。Program SHA-256は`f52f120b11a0e8eb1b41c8803afcc070645f2f732fd4c2487b423f3b94df84f6`、output binary SHA-256は`5d1b2cc01152acfc2b5bfdac2d79fadad45c2324bdb8e26c4fdb54d7bbcbd247`、75,151,196 bytesである。外部exact codeは39件のまま、`public/`・`data/`差分は0件である。

独立受入は初回High 0 / Medium 1 / Low 0で、Preflightの両context排他が個別process再検査より後になる点を指摘した。排他検査を先行させて再実行し、High 0 / Medium 0 / Low 0でPASSした。同一source SHAのhosted影響試験は後続で実施する。
