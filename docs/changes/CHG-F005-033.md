# CHG-F005-033 lease予約後・rename予約前directory writeの完全候補限定再結合

## 変更理由

commit `f56ca6f1fd970373333f87c331f4ac9fe9fbd3f0`のActions run `31028376915`は、attempt 1と3で`audio-renamed`後に`F005_ETW_PID_NOT_JOB_MEMBER_SYSTEM_DIRECTORY_BOUND_LEASE_RENAME_WRITE_REJOIN_AFTER_LEASE_RESERVATION`、attempt 2で`wav-validated`後に既知の`F005_ETW_PID_NOT_JOB_MEMBER_SYSTEM_PROCESS_BOUND_FILE_OBJECT_REJOIN_LEASE_MISSING`へ安全停止した。CHG-F005-032/T-106の専用14 stageはlocal受け入れをPASSしたが、前段のdirectory write分岐によりhosted到達を確認できていない。

## 予定変更

これまで拒否していたSystem directory writeのうち、`AFTER_LEASE_RESERVATION`だけを次の完全tupleで再評価する限定認可拡張とする。全件一致時だけ、保持中のprocess handleとlease保存値で同一性を確認した元のactive lease worker世代へ再結合する。

- authorization failureが`BIRTH_MISSING`、PIDがSystem、eventが`write`、event FileObjectが非zeroかつ未結合である。
- active phaseが`voice`で、lease phase instanceが一致する。
- 観測pathはcache内の既知directoryで、directory snapshot/current identity、同一phase root owner、root activeが一致する。
- active leaseは観測directory直下、open、FileObject・snapshot・bindingが存在し、binding path/identityがlease snapshotと一致する。
- lease current pathはrename後に欠落し、pending rename targetが同じdirectory直下に存在してlease snapshot identityと一致する。
- rename予約QPCはlease current-path予約QPCより後で、event QPCはlease予約後かつrename予約QPC以下である。
- leaseの保持process handleから得たPID、`ProcessStartKey`、`ProcessSequenceNumber`が、lease保存済みの`WorkerPid`、`ProcessStartKey`、`ProcessSequenceNumber`と完全一致する。processがaliveならJob所属を必須とし、signaledなら既存の正常終了後遅延event規則だけを許可する。process wait、identity取得、Job照会の異常・不一致は固定codeで拒否し、返却するproducer PID/sequenceはlease保存値だけを使う。
- 認可直後から`ObservationRecord`投入直前までの同一lock内で、directory current identity、旧lease pathの欠落、pending target current identityとlease snapshot identityの一致、lease FileObject bindingのpath/identityをすべて再照合する。一つでも変化・取得失敗があれば固定codeで停止し、既存の観測directory単独`expectedIdentity`再照合には依存しない。

一条件でも不一致なら既存の固定診断へ流す。`event QPC <= lease予約QPC`は拒否、`lease予約QPC + 1 tick`と`event QPC == rename予約QPC`は完全tuple評価候補、`rename予約QPC + 1 tick`は拒否して既存後段診断へ流し、`rename予約QPC <= lease予約QPC`も拒否する。`AFTER_LEASE_RESERVATION`以外、tuple不一致、旧exact code、未知suffixは認可しない構造とする。再結合後も容量actualは既存ETW observationから再計算し、候補保存・公開条件を変更しない。raw path、QPC、identity、FileObject値は公開しない。

## 影響範囲

`tm.json`とFUN-F005-047の容量guard経路から、`REQ-F005-012`、`REQ-F005-013`、`DES-F005-006`、`FUN-F005-047`、`UT-F005-047`、`IT-F005-005`、`QT-F005-008`を影響対象とする。

## 承認

既承認の容量guard内で完全tupleに限ったdesign変更であり、要求承認ゲートは設けない。影響文書更新、独立レビュー、影響試験、hosted再試験まで`in-review`とする。

計画レビューは初回High 0 / Medium 3 / Low 0を受け、元lease worker世代照合、4点TOCTOU再照合、QPC境界試験を追記した。再レビューはHigh 0 / Medium 0 / Low 0でPASSした。

## 試験方針

- native規則試験で、保持process handleのPID・`ProcessStartKey`・`ProcessSequenceNumber`、alive時Job所属、signaled時遅延event条件、wait/identity/Job照会異常、返却producer tupleを個別に固定する。
- QPC境界を`event <= lease`、`lease + 1 tick`、`event == rename`、`rename + 1 tick`、`rename <= lease`で固定する。
- 認可直後のdirectory identity、旧lease path、pending target identity、FileObject bindingの各再照合失敗を個別の固定codeで停止させる。
- `AFTER_LEASE_RESERVATION`以外、tuple不一致、旧exact code、未知suffixが認可経路へ入らない構造試験を行う。
- TypeScript/runnerでは固定codeだけを伝播し、生値非公開、容量actual再計算、candidate・`public/`・`data/`差分0を確認する。

## 実装結果

System directoryの`RENAME_AFTER_LEASE_RESERVATION`分岐を従来のdirectory単独認可より前へ追加し、完全tuple一致時だけlease保存済みPID/sequenceへ再結合するよう実装した。保持process handleはPID・start key・sequenceを取得してからwait状態とJob所属を確認し、signaled状態は完全な遅延event tupleなしでは認可しない。認可後は同一lock内でdirectory、旧lease path、target、bindingを再照合し、異常は`ETW_SYSTEM_DIRECTORY_AFTER_LEASE_REJOIN_*`の固定9 codeへ限定した。

native規則試験は210件、関連Vitestは122件、型、ESLint、同一SHA再現build 2回をPASSした。TypeScript bridge/runnerは固定code allowlistと未知suffix拒否を検証し、`public/`・`data/`差分は0件である。Program SHA-256は`7b70cc7b7c6c2c9be3efaf335376114ea135749dbecc028a37e1d370d9b60d3d`、binary SHA-256は`307c7c27388fbd19167c996b9469b82948705ec957e8be471f7aa4e9f7b3fa06`、75,040,604 bytesである。独立受入はHigh 0 / Medium 0 / Low 0でPASSし、hosted再試験を後続で実施する。
