# CHG-F005-072 ETW常時監視から事後検証への置換

## 変更理由

### 実測

F005は2026-07-29に開始し、2026-08-13までの16日間で次を費やした。

| 項目 | 実測 |
| --- | ---: |
| F005関連commit | 169 |
| 変更管理文書 | 71（CHG-F005-001〜071） |
| タスク | 81 |
| 生成されたWAV | 0 |
| batch状態 | `draft`、3作品すべて`pending` |

夏目漱石の3作品は状態遷移の最初の一歩も進んでいない。

### 音声生成は成功している

hosted production runは毎回 `temporary-written → wav-validated → audio-renamed` まで
到達している。WAVは生成され、検証され、rename済みである。
その直後の `F005_VOICE_NATIVE_OBSERVE_FAILED` で全成果を破棄している。
**失敗しているのは作業ではなく、作業を証明する仕組みである。**

### 収束しない理由

停止コードの推移を時系列で見ると、いずれもPID 4（Systemプロセス）由来である。

- `CACHE_WAV_FILE_DONE_ID` — 書込み完了済みWAVへの同一identity遅延System SetInfo
- `COMPLETED_WRITE_REJOIN_AFTER_COMPLETION_WITHIN_500MS` → `_2S` — 完了後500ms〜2秒の遅延
- `PID_NOT_JOB_MEMBER_SYSTEM_DIRECTORY_*` — cache directoryへのSystem書込み
- `EVENT_FO_OTHER_EVENT_DIR`（CHG-F005-070） — そのdirectory自身のhandleへのevent

これらはWindowsのキャッシュマネージャによる遅延書き戻しと、directory metadataの更新である。
**自分自身が書いたデータをカーネルがディスクへ反映している正常動作を、
帰属不能イベントとして停止している。**

さらに共有hosted runner上で観測されうるカーネルファイルイベントの集合は閉じていない。
1つを固定分類すると次の変種が現れる。外部診断codeは90→97→103→108と増え、
停止点は深くなるが終端しない。**全イベントの帰属を要求する常時監視は原理的に収束しない。**

## 変更内容

### 要求の改訂

REQ-F005-012とREQ-F005-017の受入基準のうち、
「phase実行中の全カーネルファイルイベントをETWで逐次相関し、帰属不能なイベントを
fail-closedとする」部分を、次の事後検証契約へ置換する。

**phase前後のワークスペース実測状態の差分が、宣言済みmutation集合とexactに一致すること。**

保証する性質は変えない。

| 性質 | 現行（常時監視） | 改訂後（事後検証） |
| --- | --- | --- |
| 不正な書込みがない | ETWで全eventを帰属 | phase前後の差分が宣言集合とexact一致 |
| 容量が守られた | phase journalのactual | 同左（変更なし） |
| path/reparse/hardlink安全性 | 書込み時に検査 | 差分対象の全pathを既存`resolveSafeWorkspaceFile`で再検査 |
| secret混入なし | 既存検査 | 同左（変更なし） |

### 契約の詳細

`beginPhase(phase, workId, phaseInstanceId)` で、追跡対象root配下を列挙して
baseline snapshotを取る。各entryはworkspace相対POSIX path、bytes、SHA-256、
native identity（volume serial + file id）、reparse point有無、hardlink数を持つ。
空き容量も同時に記録する。

`observeMutation(notice)` は**宣言の記録のみ**を行う。ETW相関を要求せず、
sequence連番・phaseInstanceId一致・path正規化・kind妥当性だけを検証する。
帰属不能なカーネルeventによる停止は行わない。

`endPhase(phase, phaseInstanceId)` で追跡対象rootを再列挙し、次を全て満たすことを検証する。

1. **完全一致** — baselineとactualの差分（created / modified / renamed / deleted）が、
   宣言済みnotice列をsequence順に畳み込んだ期待状態と、path・最終SHA-256・bytesまで一致する。
2. **余剰なし** — 宣言されていないpathの新規出現・変更・消失が0件である。
3. **安全性** — 差分対象の全pathがreparse pointでなく、hardlink数1であり、
   既存`resolveSafeWorkspaceFile`の解決結果とidentityが一致する。
4. **容量** — phase中に記録したactual peakと最小空き容量がforecast以内であり、
   最大同時書込み後も5 GiB以上残っている（REQ-F005-012の既存基準を維持）。

いずれか不成立ならfail-closedとし、raw pathを出さない固定codeで停止する。

### 失う性質と、それを許容する根拠

事後検証は「phase中に一時的に書かれ、endPhaseまでに元へ戻された書込み」を検出しない。
一方で次の理由から、総合的な厳密性はむしろ向上する。

- 現行方式はETWバッファ溢れ・event欠落時に**検出漏れ**が起こりうるが、
  事後検証は最終状態を直接測るため取りこぼさない。
- 現行方式は遅延書き戻しの完了前に判定するため、**判定時点の状態が最終状態と異なる**。
  事後検証はphase完了後に測るため、この不整合がない。
- 「一時的に書いて戻す」攻撃は、最終状態が宣言と一致する以上、成果物には影響しない。

### 適用範囲

voice phaseに適用する。他phaseの既存契約、認可条件、候補保存条件、公開条件、
容量actualの算出、`public/`・`data/`は変更しない。
ETW native guardのコードは削除せず、当面は互換のため残す。

- `f005-voice.ts` の recorder へ配線した。`beginPhase`でbaseline実測、`observeMutation`で

- `scripts/f005-run-work.ts` で走査対象を `content` / `data` / `public` と
  実際に書込む `.cache/f005-voice-*` staging に限定して有効化した。
- native `ReceiveNotice` の `Monitor.Wait` によるETW相関待ちを廃し `record.Declare()` で受理する。
  `EndPhase` / `CloseJournal` は `declared` を正常として扱う。
- rename準備・create宣言・EndPhaseのETW由来lease相関要求を外した。
  未解決write leaseの検査は維持している。

local検証: native 1286件、固定target 6本、Vitest 1308件、typecheck、ESLint、
同一SHA再現build 2回をいずれもPASS。

### 実装中に判明した設計上の落とし穴

いずれも配線前にコード実測で発見し、事後検証が同じ罠にはまるのを防いだ。

1. voice pipelineは**絶対path**でmutationを宣言する。workspace相対で走査する設計と
   噛み合わず、そのままでは全WAVが `DECLARED_MISSING` になる。正規化を追加した。
2. stagingは `content` / `data` / `public` の**外**（`.cache/f005-voice-*`）にある。
   走査rootを呼出側から渡す形にし、範囲外宣言は `PATH_OUT_OF_SCOPE` で検出する。
3. 「宣言外の既存ファイル改変」が内容不一致と誤分類されていた。宣言済みpath集合で区別する。

### 診断経路の是正

hosted停止が `F005_CAPACITY_GUARD_REJECTED` という catch-all へ潰れ、原因が特定できなかった。
nativeのGuardExceptionは全て固定識別子（補間9件も `ETW_*_{hresult:x8}` のみ）で生pathを
含まないため、未分類でも `F005_NATIVE_` 接頭辞で透過するようにした。
さらに runner 側 `safeFailureCode` の allowlist でも同接頭辞を通す。
これにより停止理由が自己記述的になり、以降の診断コストが下がる。

### hosted結果

| run | 停止点 | 意味 |
| --- | --- | --- |
| `31687597934` | `temporary-written` / catch-all | 実装反映を確認。ETW相関起因の停止は解消 |
| `31688346275` | 同上 | lease相関要求の解除だけでは未解決 |
| `31689359741` | 同上 / `code: null` | runner allowlistが原因コードを落としていた |
| `31690039263` | `temporary-written` / `F005_NATIVE_WRITE_LEASE_TUPLE_MISMATCH` | **原因を特定** |

停止点は従来の `audio-renamed` 到達後のETW帰属問題から、その**手前のwrite lease**へ移った。
`tupleMatches` は `lease is not null && WorkerPid一致 && PhaseInstanceId一致 &&
RelativePath == from` であり、`lease.rename()` の時点でこのいずれかが崩れている。

`pendingWriteLease` は reserve で設定され、write completion（`state = "completed"`）で
`null` へ戻る。ETW相関を待たなくなったことで完了の到達時刻が変わり、rename前に
leaseが解放されている可能性が高い。ただし現時点で**推定であり未確定**である。

### 停止点の推移（続き）

| run | 停止点 | 判明したこと |
| --- | --- | --- |
| `31690805619` | `temporary-written` / `WRITE_LEASE_TUPLE_MISMATCH` | 分割したが同codeのまま。**3箇所から投げられている**ことが判明 |
| `31691070353` | 同上 | `ValidateWriteLeaseTuple`も分割。なお同code＝最終fallback |
| `31691659476` | **`audio-renamed`** / `PREPARE_TUPLE_MISMATCH` | `CanPrepareRename`の入力に`correlationReady`が残っていた。是正して**過去最深へ前進** |
| `31692313652` | `audio-renamed` / `F005_CAPACITY_IPC_FAILED` | drainバイパス後、TS側のIPC検査で停止 |

`temporary-written` から `audio-renamed` への前進は、write leaseのrename経路が
事後検証契約下で正常動作するようになったことを意味する。

### 判明した構造的事実

write-through lease と write completion drain は**広範にETWへ結合している**。

- rename可否判定の入力 `correlationReady`（ETW由来のFileObject/Snapshot）
- 完了準備の `PrepareTupleMatches` と、その後段の `filesByObject` binding・
  `observations` によるdirectory owner照合
- 完了時のseal遷移

これらを述語単位で緩める作業は、hosted run 1回あたり約8分を要し、
1回につき次の結合が1つ現れる。**CHG-F005-001〜071と同じ形の開いた探索になりつつある。**

TS側の `F005_CAPACITY_IPC_FAILED` も23箇所から投げられるcatch-allであり、
分割すれば同じ反復に入る。

### 推奨する次の一手（未実施・要判断）

**voice phaseの書込みを native guard の write-through lease 経由にするのをやめる。**

write-through lease は「ETWで検証された書込み」を提供するために存在した。
事後検証契約ではその保証は phase 前後の実測差分が担う。したがって WAV は
通常の Node `fs` で staging へ書けばよく、native guard は capacity 計測と
安全path解決だけを担当すればよい。

この切り方なら、残る失敗の class 全体が一度に消える。述語を1つずつ緩める
現在の進め方より確実で、かつ CHG-F005-072 の趣旨に沿う。

- hosted は `audio-renamed` まで到達（F005開始以来の最深）。
