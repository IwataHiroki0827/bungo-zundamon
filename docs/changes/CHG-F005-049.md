# CHG-F005-049 completed no-lease directory handoff candidate多重性診断

## 変更理由

CHG-F005-048のProgram pin `db59663c44f5cb18dd66882f1ab8c721ef17c3e574fe509f1f6a1a5551ff8018`によるhosted productionは、attempt 2/3で`F005_ETW_WRITE_COMPLETION_DRAIN_LATE_DIAG_WRITE_ACTIVE_LEASE_MISSING`へ安全停止した。

初回設計は既存`CanHandoffCompletedNoLeaseDirectory`の12 predicateを個別分類する案だったが、実現性レビューにより到達不能と判定した。`broad`はSystem/BIRTH_MISSING、writeまたはsetinfo、nonzero FileObject、active voice、seal phase reference、currentまたはparent pathを保証し、`lateCandidates`はcompletion upper存在、event upper後、path別proofを保証する。aggregate `WRITE_ACTIVE_LEASE_MISSING`はeventがwrite、sealがCompletedRetained、event pathがparent、pending active leaseなしを先行分類済みであり、これとparent側proofを組み合わせるとFileObject unboundも成立する。したがってlate candidate exact 1件なら12 predicateは全trueとなり、CHG-F005-047の既存handoffを既に通過する。

観測codeが残るのは、同じ`WRITE_ACTIVE_LEASE_MISSING`へ分類されたdistinct late candidateが2件以上あり、単一candidate入口を満たさない場合である。認可・stateを変更せず、このcandidate多重性だけを生値なしの固定codeへ分離する。

## 変更内容

### 1. production共有cardinality純粋規則

production共有純粋規則`CompletedNoLeaseDirectoryHandoffCardinalityFailureCode`は、late candidate countとaggregate failure codeだけを受け取る。aggregateが`F005_ETW_WRITE_COMPLETION_DRAIN_LATE_DIAG_WRITE_ACTIVE_LEASE_MISSING`かつcountが2以上の場合だけ、次の固定codeをoverrideとして返す。

`F005_ETW_WRITE_COMPLETION_DRAIN_COMPLETED_NO_LEASE_DIRECTORY_HANDOFF_CANDIDATE_AMBIGUOUS`

code長は88文字である。countが1ならoverrideを返さず、CHG-F005-047の既存`CanHandoffCompletedNoLeaseDirectory`を一切変更せず実行する。countが0、負値、別aggregateならoverrideを返さず、呼出元が保持する既存failure codeを維持してfail-closeする。count比較は加算・乗算を行わず、`int.MaxValue`でもoverflowしない。

2件以上のcandidate内容や列挙順は結果へ影響させない。同一causeの2件を逆順にしても同じ`CANDIDATE_AMBIGUOUS`を返す。規則は候補配列、ledger、seal、lease、phase、proof、queue、generation handle、semantic map、capacity、notice、Observationを参照・変更しない。

### 2. same-gate線形化と非fall-through

`lateCandidates`のarray snapshot作成、aggregate算出、cardinality分類、ambiguous時の既存late terminal throw、またはexact 1時の既存handoff完了までを、現在の`ObserveEtw`から取得した同一`gate` lock acquisition内で行う。この区間に`Monitor.Wait`、`Monitor.Exit`、lock解放/再取得を置かず、cardinality decisionはsnapshotの`Length`と算出済みaggregateだけを使用して`writeCompletionSeals`やmutable stateを再読込しない。exact 1はgateを解放せず現在の既存handoff predicate再検査へ進み、新規のmutable rereadを追加しない。

target aggregateかつcount 2以上ではfailureを`CANDIDATE_AMBIGUOUS`へ置換して既存terminal throwへ渡す。post-request SetInfo、active-directory handoff、active-producer birth、known-directory認可、proof admission、replay、capacity、apply、candidate保存へfall-throughしない。exact 1では新規分岐・再検査・state更新を追加せず、現在のcompleted-no-lease handoffと、その後のknown-directory完全認可、OtherBound proof、immutable context、admit前/capacity前再検査をそのまま実行する。

別threadがsnapshot直後にseal/phase/lease/ledgerを変更しようとしてもgate外で待機し、分類とthrowまたは既存handoffが線形化した後にだけ進入できる。ambiguous停止時は全semantic stateと内部証拠を変更しない。

### 3. 外部契約と生値非公開

上記1 codeをcompletion-drain 49 codeへ追加して50 codeとし、native reply、TypeScript bridge、runner、workflow annotationをexact同期する。予約fence 4 codeは不変とする。全codeを127文字以下に保ち、unknown、extra suffix、exact 128文字は既存genericへ正規化する。

native reply、journal、runner serialization、workflow annotationは固定codeだけを伝播し、candidate count、candidate順序、raw path、QPC、FileObject、identity、PID、sequence、handleを含めない。IPC keys、候補選択、exact 1 handoff認可、proof/ledger、semantic state、capacity、candidate branch、Pages、`public/`、`data/`条件は変更しない。

## 試験方針

- pure cardinality ruleへcount `-1`/`0`/`1`/`2`/`int.MaxValue`と対象/非対象aggregateを投入する。対象aggregateの2以上だけ新code、1は既存handoff、0/負値/別aggregateは既存fail-closeを維持することを固定する。
- 同一causeのdistinct candidate 2件を順序入替えして同じcodeとなること、snapshot入力と全semantic stateを変更しないことを確認する。
- exact 1は既存`CanHandoffCompletedNoLeaseDirectory`のpredicate、known-directory認可、OtherBound proof、context、再検査、非fall-throughを変更しないことを構造・回帰試験で固定する。
- ambiguousは既存terminal throwへ到達し、post-request/active-directory/active-producer/known-directory認可、proof admission、capacity/applyへfall-throughせず、files、allocated、deferred、observations、notices、pending lease、peak、free、ledger、queue、generation handleを変更しないことを確認する。
- array snapshotから分類/throwまたは既存handoffまで同一gateであり、`Monitor.Wait`/`Monitor.Exit`/再lock/`writeCompletionSeals`再列挙がなく、cardinality decisionがsnapshot `Length`と算出済みaggregate以外を再読込せず、exact 1へ新規mutable rereadを追加しないことを構造検査する。実Task/barrier fixtureではsnapshot直後のseal/phase/lease/ledger driftをgateで待たせ、ambiguous decisionとsemantic fingerprintが不変であることを確認する。
- sentinel candidate count/path/QPC/PID/FileObject/identity/sequence/handleを入力し、native reply、journal、runner serialization、workflow annotationのいずれにも出現せず、固定codeだけが伝播することを確認する。
- completion-drain 50 code、予約fence 4 code、127文字上限、unknown/extra/exact 128文字generic化をnative/bridge/runner/workflowで同期する。
- native規則、関連Vitest、typecheck、ESLint、trace_check、再現build 2回、独立受入、同一source SHAのhosted productionを実施し、candidate branch、Pages、`public/`、`data/`の非変更を確認する。

## 承認

認可・要求・容量を変更しないdesign-level固定診断変更であり、要求承認ゲートは設けない。独立設計レビュー、実装、影響試験、hosted再観測まで`in-review`を維持する。

## 独立設計レビュー

初回独立レビューはHigh 1 / Medium 2 / Low 0であった。Highは、上流`broad`/`lateCandidates`/aggregate保証によりexact 1時の12 predicate falseが到達不能で、観測原因であるcandidate 2件以上を診断できない実現性不備である。Medium 2件は、raw値がreply/journal/runner/annotationへ併記されない負試験の欠落と、snapshotからdecisionまでのsame-gate/TOCTOU不変条件の明文化・試験不足である。

12 predicate案を撤回してcandidate cardinality 1 codeへ置換し、exact 1既存handoff不変、same-gate線形化、barrier drift、全surface sentinel非漏洩、50+4 exact allowlist試験を追記した。独立再レビュー待ち。

修正後の実現性・セキュリティ再レビューはHigh 0 / Medium 0 / Low 0でPASSした。整合性再レビューのLow 1件は、`broad`がwrite/setinfo・current/parentを許し、target aggregateとparent側proofの組合せでwrite・parent・unboundを導出する保証元の記述精度であった。該当するCHG/DDを現行productionの導出へ修正後、整合性もHigh 0 / Medium 0 / Low 0でPASSした。
