# CHG-F005-048 completion drain event tuple mismatch発生源診断

## 変更理由

CHG-F005-047のproduction run `31228038981`はno-lease root directory handoffを通過し、`wav-validated`後にgeneric `F005_ETW_WRITE_COMPLETION_DRAIN_EVENT_TUPLE_MISMATCH`へ到達した。このcodeはcompletion drain lookupの候補数不一致とsealed callback再検査のtuple不一致が共有しており、どの線形化段階で停止したかを外部証拠から判別できない。

認可・proof・stateを変更せず、既存throw位置を発生源別の固定6 codeへ分離する。

## 変更内容

### 1. lookup 3分類

`WriteCompletionDrainRules.LookupFailure`はbroad candidateがある場合、次の固定3 codeを返す。

1. `F005_ETW_WRITE_COMPLETION_DRAIN_EVENT_TUPLE_LOOKUP_EPOCH_EMPTY_NO_LATE_PROOF`: epoch candidateが0件で、completion upper後かつ`ProofCandidate`を満たすlate candidateも0件。
2. `F005_ETW_WRITE_COMPLETION_DRAIN_EVENT_TUPLE_LOOKUP_EXACT_MISSING`: epoch candidateが1件以上だが、`ProofCandidate`を満たすexact candidateが0件。
3. `F005_ETW_WRITE_COMPLETION_DRAIN_EVENT_TUPLE_LOOKUP_EXACT_AMBIGUOUS`: epoch candidateが1件以上で、exact candidateが2件以上。

epoch 0かつlate candidate 1件以上は既存generic late→late aggregate/handoff経路を維持する。broad 0は従来どおりnot handled、epoch>0かつexact 1件はPASSとする。候補数の負値、`exact > epoch`、epoch 0なのにexact非0、lateとepochの同時存在など純粋規則の矛盾入力は既存generic `EVENT_TUPLE_MISMATCH`へfail-closeし、production呼出し前提を構造試験で固定する。

### 2. sealed callback再検査3分類

`RecheckSealedCallbackLocked`はsnapshotのSealSequenceに一致するseal数を先に分類する。

1. `F005_ETW_WRITE_COMPLETION_DRAIN_EVENT_TUPLE_RECHECK_SEAL_MISSING`: 0件。
2. `F005_ETW_WRITE_COMPLETION_DRAIN_EVENT_TUPLE_RECHECK_SEAL_AMBIGUOUS`: 2件以上。
3. `F005_ETW_WRITE_COMPLETION_DRAIN_EVENT_TUPLE_RECHECK_FIELDS`: sealが1件だが、phase reference、seal state、normal/post-request replay排他、proof存在/kind/FileObject/generation/state/path、producer PID/sequenceの既存複合tupleが不一致。

現行`PostRequestReplayTupleMatches`はseal/proof identityまでbool入力に含め、identity falseをtuple throwへ吸収する。これをidentity非依存の`PostRequestReplayFieldsMatch`へ分離する。fields側はreplay kind、setinfo、current path、seal CompletionRequested、completion/deadline存在、`completion < event <= deadline`、completed record不存在、proof kind/generation/state/path、producer PID/sequenceだけを評価する。fields通過後にseal current identityとproof identityを既存共通identity検査へ渡し、どちらか一方でもfalseなら従来の`F005_ETW_WRITE_COMPLETION_DRAIN_EVENT_IDENTITY_FAILED`で停止する。

normal replayも同じ共通identity検査を使用する。retained identity再inspection、retained process再検査は既存identity/process fixed codeを維持する。新3 codeの判定はproduction共有純粋規則へ切り出し、同じ既存throw位置から停止する。field個別軸の追加認可や値公開は行わない。優先順位はseal count→fields→identity→retained identity→processである。

### 3. 外部契約

上記6 codeを既存completion-drain 43 codeへ追加して49 codeとし、native reply、TypeScript bridge、runner、workflow annotationを同期する。旧generic `EVENT_TUPLE_MISMATCH`は矛盾入力と後方互換のため集合に残す。全codeを127文字以下とし、raw path、QPC、候補数、FileObject、identity、PID、sequence、handleをreply/journal/annotationへ追加しない。

候補選択、handoff、proof admission/commit、ledger、queue、generation handle、semantic map、capacity、notice、Observation、seal/lease/root state、予約fence4 code、IPC keys、candidate保存、Pages、`public/`、`data/`条件は変更しない。

## 影響範囲

`tm.json`の`DES-F005-006`/`DES-F005-012`から機械抽出した候補のうち、本変更を直接担う`REQ-F005-012`、`REQ-F005-013`、`FUN-F005-017`、`FUN-F005-047`、`UT-F005-017`、`UT-F005-047`、`IT-F005-005`、`QT-F005-008`、`QT-F005-009`と、`T-070`、`T-121`、`T-122`を影響対象とする。

## 試験方針

- lookupへbroad/epoch/exact/lateの0/1/2境界を投入し、3新code、late既存経路、PASS、矛盾genericを排他的に固定する。
- production呼出しがepoch 0時はlate候補数、epoch正時はexact候補数を渡し、候補列挙やProofCandidateを変更しないことを構造検査する。
- sealed recheckのmatching seal 0/1/2と複合tuple all true/各falseをproduction共有規則で固定する。post-request nested fieldsはevent kind/path、completion/deadline存在、QPC下端/上端、completed record不存在、proof kind/generation/state/path、producer tupleを各1 falseにする。fields all true後にseal current identityとproof identityを各1 falseにし、両方とも既存EVENT_IDENTITY_FAILEDとなることを固定する。retained identity/process failure codeは非変更とする。
- 6新codeがlookup/recheckの該当throw位置だけで使われ、診断後にhandoff/認可/applyへfall-throughせず全semantic stateを変更しないことを確認する。
- completion-drain 49 code、予約fence4 code、127文字上限、unknown/extra/exact 128文字generic化をnative/bridge/runner/workflowで同期する。
- native規則、関連Vitest、typecheck、ESLint、trace_check、再現build 2回、独立受入、同一source SHAのhosted productionを実施する。

## 承認

認可・要求・容量を変更しない固定診断変更であり、要求承認ゲートは設けない。独立設計レビュー、実装、影響試験、hosted再観測まで`in-review`を維持する。

## 独立設計レビュー

初回レビューはHigh 0 / Medium 1 / Low 0であった。Mediumは、現行post-request replay純粋規則がidentity 2軸をtuple boolへ含むため、単純なFIELDS置換では既存EVENT_IDENTITY_FAILEDを維持できないという指摘である。post-request fieldsとidentity検査を分離し、nested fields全軸とidentity 2軸のone-false、seal count→fields→identity→retained identity→processの優先順を明記した。

修正後の独立再レビューはHigh 0 / Medium 0 / Low 0でPASSした。proof nullの先行停止を含むfields規則、identity既存throwへの到達、全one-false、lookup/49+4 code、state非変更が現行productionへ安全に実装可能と判定された。
