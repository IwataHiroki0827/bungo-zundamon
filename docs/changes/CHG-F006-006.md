# CHG-F006-006 F006最終Catalog統合・固定v0.5.0回帰・公開tree候補を作成する（T-154完結）

## 経緯

T-151/T-152/T-153完了によりF006の3作品（山月記000624・名人伝000621・弟子001738）が
全てaccepted状態となった。T-154では、F005の`scripts/f005-final-integration.ts`と
同じ役割を果たす最終統合scriptを新設し、3作品を累積結合した単一の公開tree候補を
生成する。

## 実施内容

### 1. `scripts/f006-final-integration.ts`を新設

F005の`f005-final-integration.ts`の構造（clean source commit検証→3作品分の
fragment片を組み立て→baseline結合→`buildIntegratedPublicTree`(`prepare-release`
モード)→`buildPagesPreview`でdist生成→`--retain`でcandidate-paths.json永続化）を
踏襲しつつ、F006既存の`mergeNewAuthorCatalog006`（FUN-F006-011、baseline
projection exact維持のassertを内包）・`deriveF006RouteSet`（FUN-F006-012）を
使うことで、F005が独自に持っていたshumi-notice検証・predeploy再結合等の
F005固有ロジックは不要とした（F006の`F006CatalogFragment.notices`は
QA-F006 No.4の確定回答により常に空配列）。

work単位のfragment構築ロジック（`buildWorkFragmentPiece`）は
`scripts/f006-content-preview.ts`と同一構造の複製とした。同scriptはCLI引数化・
`await main()`副作用付きのため直接importできないため。
v0.5.0固定baseline不変性検証（`assertV050Invariant`）も同様に複製した。

### 2. F006 batch level `rightsSnapshotIds`欠落の是正（backfill）

script初回実行時、`loadAcceptedBatches`が`BATCH_ARTIFACT_MISSING`で停止した。
原因はF005で発生した既知の不備（CHG-F005-078）と同型: F006 batchは
`transitionBatchState('rights-verified', ...)`を一度も経由しない設計
（batch level `stageRecords`が常に空、statusはwork進捗から自動導出）のため、
3作品全件acceptedへ進んだ後も batch単位`rightsSnapshotIds`が空配列のままだった
（work単位`actualCapacityRef`は`promoteVerifiedWorkArtifacts`が正しく書込み済みで
欠落なし。CHG-F005-078がbatch.tsへ追加した後方互換拡張の恩恵）。

work状態遷移はforward-onlyであり、既にaccepted確定済みの3作品を通常フローで
やり直すことはできないため、一回限りのスクリプト
`scripts/f006-backfill-rights-snapshot-ids.ts`を新規作成（実行後も削除せず記録
として残す）し、実evidence（`content/batches/F006/source-snapshots/
selection.json`の`policies[].decision.contentSha256`、選定時2026-08-21に
取得・検証済み）から機械的に値を導出して`content/batches/F006/batch.json`へ
一度だけ書き込んだ（値は捏造せず、実ファイルをcanonical JSON一致・
`decision.decision === 'allow'`等を検証してから採用）。

実際に書き込んだ値:
- `voicevox-terms:10dbc1bafcbe612378b998e96882809970f1591194ab2851669e11805feff40b`
- `zundamon-audio-terms:902ac82a53c40ac8a5c39111b9f28cf1b1cb6d20e52e37e5264d0d2f271a6a98`
- `zundamon-character-guideline:d6309b88430273d39fcb10b7149ec0eb8b8a0cbd8aa10d6d0fc0705b22c4d947`

この書換えにより、既にaccepted確定済みの001738 work（manifest上の最終work）に
関する`.cache/transactions/accepted-audio/F006-001738.json`（idempotent再検証用
journal、gitignore対象）の`nextManifestSha256`が旧manifest hashを指したままとなり
`f006-acceptance.test.ts`の再検証テストが`WORK_ACCEPTED_AUDIO_CONFLICT`で
失敗する副作用が生じた。journal自体はcontent（accepted-audio実体・work FSM状態）
を一切変更しない冪等再検証専用の記録であるため、`nextManifestSha256`を
backfill後の実manifest hash（`hashBatchManifest`で再計算した値）へ更新する
一回限りの補正を行った（journal本体のevidence・postTreeDigest等は変更していない。
000624/000621の同種journalは元々「その作品を最後にacceptした時点」の中間manifest
hashを保持する設計であり最終manifestとは一致しないため対象外＝仕様通り）。
