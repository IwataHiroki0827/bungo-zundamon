# CHG-F005-052 T-110決定的hosted相関検証

## 変更理由

Q-042で、T-110の現行Program pinによるfollow-up productionを3 attempt実行しても、前段の既知completion-drain固定codeで安全停止し、`SYSTEM_DIRECTORY_BOUND_LEASE_WRITE_REJOIN_CANDIDATE`完全tupleの限定再結合へ到達しなかった。productionの自然なETW配送順へ繰り返し依存する方法では、認可条件を変えずに対象経路のhosted影響を有限回で確認できない。

ユーザー回答「決定的なhosted影響確認方法を別変更管理で設計」を受け、T-110の認可・容量actual・候補保存・公開条件を変更せず、同じproduction assemblyを参照するnative相関試験をGitHub hosted Windows上で実行し、対象経路だけを決定的に証跡化する。

## 変更内容

### 1. production共有規則を使う対象別CorrelationTests

`native/f005-guard-tests/F005Guard.CorrelationTests.csproj`は従来どおり`native/f005-guard/F005Guard.csproj`を`ProjectReference`し、production assemblyの`InternalsVisibleTo`で公開された次の実規則を直接呼び出す。production規則の複製、test-only分岐、条件付きコンパイル、production guardの追加IPC operation・環境変数・command line switchは禁止する。

- `SystemDirectoryBoundLeaseRejoinAuthorizationRules.EvaluateCheapPredicates`
- `IsQpcOrderValid`、`InitialTupleMatches`、`TupleRecheckFailure`
- `InitialProcessFailureCode`、`RecheckProcessFailureCode`、`ProcessRejection`
- `EvaluateInitialTupleInspection(Func<BoundLeaseInitialInspection> inspect, bool directorySnapshotAvailable, bool leaseParentMatches, bool leaseOpen, bool leaseSnapshotAvailable, bool leaseFileObjectAvailable, bool leaseBindingAvailable, bool leaseBindingPathMatches, bool leaseBindingIdentityMatches)`。`BoundLeaseInitialInspection`はdirectory/lease currentの存在・identity一致を表す4 booleanだけを持つ。production callbackのdelegateはdirectory/leaseの`TryInspect`をexact 1回ずつ実行し、共有処理はdelegateをexact 1回だけ評価して`InitialTupleMatches`へ渡す。`GuardException`は共有処理内で`ETW_SYSTEM_DIRECTORY_BOUND_LEASE_REJOIN_INITIAL_TUPLE_INSPECTION_FAILED`へ固定して再throwする。target suiteは同じ共有処理へ正常recordとthrow fixtureを渡す
- production callbackの`TryAuthorizeBoundLeaseDirectoryWriteLocked`と再照合経路が上記共有規則を同じ順序で呼ぶことを固定する構造契約

target suiteはID `CHG-F005-036/T-110`を持ち、all-true候補、cheap predicateの各単独false、QPC三境界、初回tupleの各単独false、初回inspect delegateのthrow、初回・再検査のidentity/wait/Job照会失敗、tuple mismatch、signaled、Job外、認可後tupleの各単独falseと先行code優先を個別caseとして実行する。throw fixtureはproduction共有`EvaluateInitialTupleInspection`だけへ渡し、production guardへfault入力を公開しない。さらにRUNNER_TEMPのGUID付きworkspace外rootで実directory/file identityを取得し、保持processをprivate Jobへ収容して、alive member、signaled、別generation、Job外、identity差替えを実Windows APIで検証する。test assemblyがcaller供給の合否や偽identityをPASS証拠へ変換することを禁止する。

### 2. hosted workflowと証跡契約

`.github/workflows/f005-hosted-native-probe.yml`はread-only verification専用とする。workflow全体の権限を`actions: read`と`contents: read`だけに固定し、job単位のwrite権限、git push、evidence branch更新を禁止する。checkoutは`persist-credentials: false`とし、build/test processへtokenを渡さない。既存build・kernel ETW preflight後に、固定SDK/runtimeと同じsource commitでCorrelationTestsのtarget suiteを実行する。workflow triggerへ`native/f005-guard-tests/**`を追加し、production Program、production project、test project、test sourceのSHA-256を実体から再計算する。canonical evidenceは同一runの固定base64 markerとjob summaryへ出し、local側がActions runからexact再検証して版管理証跡へ転記する。外部artifact actionとwrite tokenは使用しない。

CorrelationTestsが実際にloadしたProjectReference生成`f005-guard.dll`のSHA-256とMVID、CorrelationTests assembly/executableのSHA-256を実行process内から再計算し、source-onlyのProgram/project SHAとpinned single-file guard SHAを別fieldで保持する。`build.ps1`、`global.json`、workflow、test project、test source、case manifestのSHAも固定SDKでのbuild tupleへ結合する。single-file guard SHAだけをCorrelationTestsの実load証明として流用しない。

canonical evidenceはtarget ID、source commit、workflow run ID/attempt、runner OS/arch、runner `ImageOS`/`ImageVersion`、Windows build/UBR、PowerShell version、Program/project/build.ps1/global.json/workflow/test project/test source SHA、pinned native binary SHA、実load production assembly SHA/MVID、test assembly/executable SHA、固定SDK/runtime、kernel ETW preflight結果、case manifest SHA、期待case数、PASS case数、同一source SHAのPages run ID/attempt/conclusionとdeploy job conclusion、結果だけを含む。case名以外のpath、PID、QPC、FileObject、volume/file identity、process key/sequence、handle、Win32番号、stack、自由文を含めない。target processのstdout/stderrはRUNNER_TEMPの個別fileへ直接redirectし、各65,536 bytesを上限とする。workflowは固定case markerと最終markerだけを読み、未知行・重複marker・case不足/余分・SHA差・exit code非zeroをFAILとする。raw stdout/stderrはjob log、annotation、summary、evidenceへ転記せず、失敗時は固定codeだけを出す。

verification jobは対象試験前後でtracked `public/`・`data/`・candidate/audio/staging差分0、candidate branch不存在を確認する。`pages.yml`のbuildはfeature branch pushでも実行されるため非実行を要求しない。同じread-only jobがGitHub APIを固定workflow pathと`head_sha == sourceCommit`でbounded pollし、対応するpush run ID/attempt/conclusionとdeploy job conclusion `skipped`を取得してからcanonical evidenceを確定する。run欠落、複数active attempt、timeout、head SHA差、deploy job欠落、`skipped`以外はblockedとする。既存のproduction candidate workflow、候補保存、Pages、tag、release経路は変更しない。

### 3. T-110 hosted影響判定

T-110のhosted影響は、次の全条件を満たす単一source commitのcanonical evidenceでPASSとする。

1. pinned native guard buildとkernel ETW preflightがPASSする。
2. target suiteのcase manifest SHA・期待件数・実PASS件数が一致し、実load production assembly SHA/MVIDとtest assembly/executable SHAがsource/build/workflow tupleへ結合される。
3. all-true候補がproducer tupleを返し、各単独false・実Job/process・identity異常・認可後再照合が期待する既存19 codeまたは非認可へ排他的に収束する。
4. production callbackが同じproduction共有規則を同じ評価順で使用し、test-only入口・認可変更・後段fall-throughが存在しないことを構造検査する。
5. raw値非公開、semantic state非変更、`public/`・`data/`差分0、candidate branch不存在、同一source SHAのPages runとdeploy job conclusion `skipped`を確認する。
6. feature branch verificationがwrite tokenを持たず、checkout credential、git push、evidence/candidate branch更新、外部artifact uploadを行わない。

この証跡はT-110限定再結合のhosted影響確認にだけ使用する。通常production pipelineのend-to-end成功、候補受入、容量actual、公開判定の代用にはしない。実productionで対象stageへ自然到達した場合は従来どおり追加証拠として採用できるが、PASS条件には要求しない。

## 影響範囲

`docs/traceability/tm.json`の`FUN-F005-047`直接参照・被参照関係とT-110の既存タグから、`REQ-F005-012`、`REQ-F005-013`、`DES-F005-006`、`DES-F005-012`、`FUN-F005-047`、`UT-F005-047`、`IT-F005-005`、`QT-F005-008`、`QT-F005-009`、`T-070`、`T-110`を影響対象とする。実装・再試験タスクとして`T-126`を追加する。

## 試験方針

- target suite manifestのcase ID、順序、件数、SHAを固定し、欠落・余分・重複・順序差・偽PASS markerを拒否する。
- all-trueと全単独false、QPC同値/+1、初回inspect throwを含む初回・再検査19 code、先行code優先をproduction共有規則へ直接投入する。
- GUID付きRUNNER_TEMPで実directory/file identityとprivate Job childを用い、alive memberだけを通し、signaled、別generation、Job外、差替えを固定拒否へ分類する。
- production callbackの共有規則呼出順、test-only入口不存在、後段非fall-through、semantic fingerprint不変を構造検査する。
- evidenceのexact keys、source/build/workflow/load assembly/test binary hashとMVID、runner image/Windows/PowerShell tuple、件数、raw値非公開、unknown行generic化、workflow全体`actions: read`/`contents: read`、credential・push・artifact upload不存在、candidate branch不存在、同一source SHAのPages deploy skipを検査する。
- local native規則、関連Vitest、typecheck、ESLint、trace_check、同一SHA再現build2回、独立受入後、同一source commitのhosted target suiteを実施する。

## 承認

既承認の認可・要求・容量・候補保存・公開条件を変更せず、hosted影響確認の試験方法だけを決定化するdesign-level変更であるため、要求承認ゲートは設けない。影響文書更新、独立レビュー、T-126実装、local/hosted影響試験完了まで`in-review`を維持する。

## 独立設計レビュー

初回レビューでは、feature branch自身が変更できるworkflowへwrite tokenを与える信頼境界不備と、Pages deploy skipを同一canonical evidenceへ相関できないTOCTOUがHighとして検出された。加えて、失敗時stdout/stderrのraw値漏洩余地と共有inspect helper契約の曖昧さを修正対象とした。

production共有`EvaluateInitialTupleInspection`のdelegate・record・predicate・固定例外契約を明記し、実load production assembly SHA/MVID、test assembly/executable SHA、build/workflow hash、ImageOS/ImageVersion・Windows build/UBR・PowerShellをcanonical evidenceへ結合した。workflow全体はread-onlyにし、credential、push、artifact uploadを廃止した。同じread-only jobが同一source SHAのPages run terminalとdeploy job `skipped`をbounded pollし、target raw出力をRUNNER_TEMPへ上限付きredirectする。修正後の独立再レビューはHigh 0 / Medium 0 / Low 0でPASSした。
