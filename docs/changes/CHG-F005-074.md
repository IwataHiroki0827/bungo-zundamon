# CHG-F005-074 process開始時刻の取得を負荷に耐えるようにする

## 変更理由

001104(趣味の遺伝)のホスト生産が受理段階で停止した。

```
F005_PROGRESS=voice-generated
F005_PROGRESS=offline-build-complete
F005_PROGRESS=preview-prepared
F005_PROGRESS=acceptance-staged
F005_PROGRESS=session-closed
F005_PROGRESS=actual-measured
F005_FAILURE_JSON={"code":"F005_ACCEPTANCE_TRANSACTION_INVALID",
  "message":"current process start identityを取得できません", ...}
```

音声83件の生成・実測まで完了しており、失敗は最終の受理トランザクションである。

`readProcessStartIdentity` はWindowsで `powershell.exe` を起動し
`Get-Process -Id <pid>` の `StartTime` を読む。timeoutは5秒であった。

```ts
const result = await execFileAsync('powershell.exe', [...],
  { windowsHide: true, timeout: 5_000, maxBuffer: 4_096 });
```

同一workflowで直前に成功した001076(倫敦塔)は音声55件、失敗した001104は83件である。
83件の合成直後という最も負荷の高い時点で、Windows PowerShellの
interpreter起動が5秒を超えたと考えられる。処理内容は `Get-Process` 一回だけで、
5秒はプロセス起動そのものへの割り当てとして薄い。

## 変更内容

問い合わせ内容は変えず、待ち時間だけを段階的に延ばして再試行する。

```ts
const PROCESS_START_IDENTITY_TIMEOUTS_MS = Object.freeze([5_000, 15_000, 30_000]);
```

processが既に存在しない場合は再試行しても結果が変わらないため、
`processAlive(pid)` が偽なら即座に `null` を返して打ち切る。
これは lock保持processの生存確認経路(2159行・2223行)の意味を保つために必要である。

## 却下した代替案

**`performance.timeOrigin` から現在processの開始時刻を得る。**
subprocessを起動せずに済むが、このidentityは**他のprocessが同じpidに対して
同じ値を計算できること**が前提である(死んだprocessが残したlockを判別するため)。
現在processだけ別の導出にすると突合できなくなる。

**timeoutを一律に延ばす。**
lock保持processの生存確認は正常時にも呼ばれるため、存在しないpidの判定に
毎回30秒待つことになる。生存確認を先に行う形にして待ち時間を段階化する方が
正常時のコストを増やさない。

## 影響範囲

- `src/content/f005-acceptance.ts` — `readProcessStartIdentity`

失敗はhosted runnerの負荷に依存するため、ローカル環境では再現しない。
検証は再実行によるホスト生産の成功をもって行う。
