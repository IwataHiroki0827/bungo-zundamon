# CHG-F005-084 mainマージ後に発覚したCI red（native guard依存テストのubuntu実行不能）を解消する

## 経緯

`feature/F005`（commit `6e1f311`）が`origin/main`へfast-forward push（`957855c..6e1f311`）
された直後、GitHub Actions `pages.yml`のbuild job（ubuntu-latest上で`npm run verify`＝
`lint && test && build`を実行）が失敗した。原因はF005のnative guard
（`F005NativeGuardClient`、Windows専用のJob Object/ETW機構）に依存するテストが、
native guard自体を利用できないLinux CI環境で軒並み
`F005SourceError: native guardはWindowsでのみ利用できます (F005_PATH_UNSAFE)`
またはspawn ENOENTで失敗したことである。これは新しい問題ではなく、`STATUS.md`に
以前から「F005をmainへマージする前に、ubuntuで実行不能なnative guard依存テストの
OS gateを決める」という既知の未対応事項として記録されていたが、今回それに気づかず
mainへマージしてしまった（origin/mainのCIが赤い状態、deployジョブは未実行のため
公開中v0.4.1サイトへの実害はない）。

`gh run view 32431124995 --log-failed`で失敗ログ全文を確認し、失敗していた
テストケースを洗い出した。

- `src/content/f005-native-guard.test.ts`: 1件（`System SetInfo相関のnative規則を
  攻撃ケース込みで実行する`。Windows専用`.cache/dotnet-f005/sdk/dotnet.exe`を
  `spawn`する native単体試験自体）
- `src/content/f005-source.test.ts`: 19件（`resolveSafeWorkspaceFile`/
  `rehydrateF005SelectionSnapshot`/`rehydrateF005PredeploySnapshot`/
  `normalizeAozoraXhtmlEntities`等、native guardを間接的に前提として呼ぶテスト。
  既存の`永続化selectionの参照実体がsymlinkなら拒否する`（611行目）が
  `it.runIf(process.platform === 'win32')`で先行してOS gateされていた）
- `src/content/f005-run-work.test.ts`: 2件。うち1件
  （`hosted native guard overrideをreparse/hardlinkなしのworkspace外pathだけに
  限定する`）はWindows専用executable pathの実在を前提とする試験。もう1件
  （`manifest参照artifactは同一bytesをdurable再開し、異なる既存bytesを上書き
  しない`）はOS gateではなく、`src/content/artifacts.ts`の`syncDirectory`実装が
  `process.platform === 'win32' && nativeDirectorySync`の場合だけcallbackを
  経由し、POSIXではdirectory handle直接fsyncへfallbackするという実設計上の
  分岐によるもの
- `src/content/artifacts.test.ts`: 1件（同じ`syncDirectory`のOS分岐により、
  `directorySync` callbackが記録する`native-directory-flush` phaseが
  POSIXでは発生しない）

## 決定

既存の`it.runIf(process.platform === 'win32')`パターン（`f005-source.test.ts:611`）
を踏襲し、native guard自体または実在するWindows専用executableを直接的・間接的に
要求するテスト22件をすべて同パターンでOS gate化した。`src/content/artifacts.ts`の
`syncDirectory`実装で正当なOS分岐が存在すると確認できた2件（`f005-run-work.test.ts`・
`artifacts.test.ts`）は、gateではなく`process.platform === 'win32'`に応じた
期待値分岐へ変更した。src本体の動作ロジックは一切変更していない（テストの
gate・期待値のみ）。

## 影響範囲

- `src/content/f005-native-guard.test.ts`: 1テストをOS gate化
- `src/content/f005-source.test.ts`: 12箇所（`it.each`1件を含む、実質19サブケース）
  をOS gate化
- `src/content/f005-run-work.test.ts`: 1テストをOS gate化、1テストを期待値分岐化
- `src/content/artifacts.test.ts`: 1テストを期待値分岐化

## 検証

- `npm run lint`: PASS
- `npm run typecheck`: PASS
- `npx vitest run`（フルスイート、Windows）: 1319件中1313 PASS・6 failed。
  失敗6件は本CHGで変更していない`baseline.test.ts`（2件）・`batch-runtime.test.ts`
  （1件）、および本CHGで変更した`f005-native-guard.test.ts`（1件、既存gate済み
  別テスト）・`f005-source.test.ts`（2件、本CHGで新規gateしたテスト2件）で、
  いずれも`Test timed out`または`EBUSY`によるWindows並列実行時のresource
  contentionと判断した。
- 上記6ファイルを個別実行（`npx vitest run src/content/baseline.test.ts
  src/content/batch-runtime.test.ts src/content/f005-native-guard.test.ts
  src/content/f005-source.test.ts src/content/f005-run-work.test.ts
  src/content/artifacts.test.ts`）した結果、142件全PASSを確認し、並列実行時の
  リソース競合によるflakyであると裏付けた。
- Linux実行環境（Docker）はDocker Desktopが起動していなかったため、今回は
  実行できなかった（未検証）。代わりにコード上の根拠を確認した。
  - OS gate化した22件は`process.platform === 'win32'`が偽であるLinux上では
    `it.runIf`により確実にskipされる（vitestの`runIf`はcondition偽時に
    `it.skip`相当へ切り替わる標準API）。
  - `f005-run-work.test.ts`の期待値分岐と`artifacts.test.ts`の期待値分岐は、
    分岐先の実装（`src/content/artifacts.ts`の`syncDirectory`、167行目
    `if (process.platform === 'win32' && nativeDirectorySync)`）を直接参照して
    導出したものであり、CI失敗ログの実際の差分
    （`expected [] to deeply equal [...(2)]`、
    `expected [...(2)] to deeply equal [...(3)]`）とも整合する。
