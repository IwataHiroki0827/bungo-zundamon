# CHG-F005-038 completion drainの不変binding proof・retained identity再生

## 変更理由

commit `8b262d42ee7ea5e79f54c26d63689dba6488975f`のActions run `31124047021`は、3 attemptすべてで`audio-renamed`後のCHG-F005-037 completion drain replayへ到達した。attempt 1は`F005_ETW_WRITE_COMPLETION_DRAIN_EVENT_IDENTITY_FAILED`、attempt 2/3は`F005_ETW_WRITE_COMPLETION_DRAIN_BINDING_MISMATCH`で安全停止し、candidate branchは未作成、Pages deployはskipとなった。

Q-037で「CHG-F005-038で不変replay proofへ修正」が回答され、T-111のブロックを解除して本変更管理を再開した。

`PendingCallbackSnapshot`はcallback時のidentityを保持しているが、lookupとreplay時に`TryInspect(snapshot.NormalizedPath)`でrename後のpathを再openし、FileObject互換性も現在の`filesByObject`で再評価している。さらに`CompleteWrite`と`EndPhase`はseal current/parent pathとlease FileObject bindingを同じ可変path/mapから再照合する。`FileIOCleanup → ForgetFileObject`はcallback admission、event counter、queueの外で`filesByObject`を直接削除するため、final再照合と競合する。これらの可変入力が、同一source SHAの結果をidentity失敗とbinding不一致へ分岐させた。認可対象や容量計算を広げず、callback受理時に成立した証跡を不変化して再生する。

## 予定変更

### 1. sealのretained object handle

`prepareWriteCompletion`の既存tuple検証後、sealed current fileはdesired access `0`、share read/write/delete、`OPEN_REPARSE_POINT`、parent directoryは同じ条件に`BACKUP_SEMANTICS`を加えたmetadata-only handleで各1件保持する。handle取得直後と各再inspectionでvolume ID、FileId128、hardlink数、reparse属性を検査し、既存の`CurrentIdentity`/`DirectoryIdentity`と一致しない場合はprepareを拒否する。最大128 sealに対して最大256 handleへ固定する。current取得後のdirectory取得失敗、deadline timeout、`PoisonLocked`の反復、session abort/Dispose、`released`遷移、journal closeを同じ所有者のidempotent disposeへ集約し、部分取得を含む全handleをexactly onceだけ解放する。

retained handleはrename後も同じfilesystem objectを指すため、replayではevent pathを再openしない。current eventはcurrent handle、parent eventはdirectory handleからvolume/FileIdを再inspectionし、snapshotのcallback時identityとseal identityの三者一致を必須とする。handle無効、inspection失敗、identity差、reparse/hardlink不安全は既存の`F005_ETW_WRITE_COMPLETION_DRAIN_EVENT_IDENTITY_FAILED`へ閉じる。容量のlogical/allocated値とfree bytesは従来どおりcallback時snapshotをETW sequence順に適用し、retained handleから後時点の容量値を逆流させない。

### 2. event-time FileObject binding ledgerと全queue object proof

semantic state用`filesByObject`とは別に、callback配送順だけを表すbounded `WriteCompletionBindingLedger`をcompletion drain期間中に保持する。最初の`prepareWriteCompletion`は通常のpipe用`lock (gate)`分岐へ入れず、`callbackAdmission.EnterFinal()`を取得して既存callbackをaccountedまで完了させ、新callback entryを遮断してから`gate`を取得する。この区間で`filesByObject`をimmutable baselineへ複製し、各baseline bindingのmetadata-only retained handleを開いてidentityを再照合した直後をledgerの線形化点とする。writer待機前にread tokenを取得済みのcallbackはbaselineへ反映済み、writer待機後のcallbackはbaseline後proofへ一意に所属させる。

baselineではFileObjectごとに、存在しない状態をgeneration `0`、存在するbindingをgeneration `1`へ固定し、`proofSequence = admissionHead = appliedCursor = 0`から開始する。後続bootstrap/rebindだけがそのFileObjectのgenerationをchecked `+1`する。全generation handleはfile/directory共通でdesired access `0`、share read/write/delete、`BACKUP_SEMANTICS | OPEN_REPARSE_POINT`を使い、取得後の属性・identity検査で種別を確定する。ledgerはcallback受理で進む`admissionHead`とbatch commitで進む`appliedCursor`を分離し、FileObjectごとのchecked単調generation、bound/retired、identity、path、retained handle、delete/cleanup seenを持つ。各sealはlease FileObjectのexact generationを封印する。Observation用`EtwSequence`とは別に、全通常proofとCleanup proof共通のchecked `proofSequence`を`gate`内で一度だけ採番してadmission headを遷移する。

- `sealed-current`のwrite/setinfoはseal exact generationがboundまたはretiredでidentity一致することを必須とし、before/afterを同値にする。
- `sealed-parent`のwrite/setinfoはcallback時unbound proofを必須とし、直近generation/stateを含むbefore/afterを同値にしてdirectoryへbindしない。
- `other-bound`の検証済みnormal non-delete eventだけは、currently unbound/retiredならchecked `generation + 1`でcurrent identityへbootstrap/rebindし、boundなら同一generation/identityを維持する。別identity上書きは必ず新generationと新handleを要求する。
- renameは`other-bound`の同じidentity/generationを維持してpathだけを遷移し、source/target不一致を拒否する。
- deleteと追跡対象Cleanupは、先着側が一致するbound generationをretiredへ遷移する。後着counterpartは同一FileObject・identity・generationならstateを変えないidempotent terminal proofとして許可し、同種duplicateだけ拒否する。generationはretire時に増やさず、後続bootstrap/rebind時だけ進める。

各`PendingCallbackSnapshot`へpath kind（`sealed-current`、`sealed-parent`、`other-bound`）、FileObject、expected identity、`generationBefore`/`generationAfter`、binding before/afterを含む`ImmutableBindingProof`を保存する。sealed current pathはevent FileObjectとseal lease FileObject/exact generationが完全一致するproofだけ、parent pathは非zeroかつcallback時unboundのproofだけをexact候補とする。最初のsealed defer後にphase-wide queueへ入る`SealSequence == null`の通常Job callbackは`other-bound`とし、そのFileObject generationのretained metadata handleをqueue適用完了まで保持する。deleteは同じgenerationで先に保持したhandleを参照する。これにより任意pathのunsealed snapshotもpath再openせずidentityを再検査できる。lookupとreplayは`filesByObject.ContainsKey`を使用しない。

`FileIOCleanup`はpath/identity/generationを持たないためObservationや容量eventへ昇格させず、`TimeStampQPC`とFileObject数値を持つ専用`CleanupBindingProof`だけを生成するledger-only callbackとする。method entryから完了まで同じcallback admission read tokenを保持し、`gate`内で共通`proofSequence`を採番する。ledgerでcurrently-bound、またはactive seal/lease/deferredに属する追跡対象FileObjectのうち、同じ数値に先行generationも後続rebindも存在せず、delete/cleanup未処理の単一generationだけをretiredへ遷移できる。delete後にrebindされる前の同一generation Cleanupはcounterpart terminalにできる。

一度でも同じFileObject数値が後続generationへ再利用された後は、pathless Cleanupを旧・新のどちらへ帰属させるか入力から証明できないため、正常unbindや新generationのretireを行わず`F005_ETW_WRITE_COMPLETION_DRAIN_BINDING_MISMATCH`でfail-closedする。旧generation Cleanupが遅延して新generation bind後に到着した場合も、ledger、semantic map、seal、lease、容量、Observationを全て無変更にする。無関係な未知/unbound cleanupは、その数値に追跡済みgeneration履歴が一度もない場合だけstate無変更でignoreし、履歴ありの曖昧cleanupと同じtracked generationのduplicate Cleanupは固定proof不一致として拒否する。lease/deferred invalidationはproof確定後に既存規則どおり適用する。cleanup relevant/accounted専用counterをfinal writerの安定条件へ含め、CompleteWrite/EndPhaseが既存cleanupのledger反映完了を待ち、新cleanup entryを遮断する。raw pathやgenerationを推測しない。

ledger dictionaryは最大8,192件、通常callback proofと追跡対象cleanup proofの合計は8,192件、pending queue snapshotは8,192件、generation retained handleは8,192件へ固定する。live retained handle総数はgeneration 8,192＋seal current/directory 256の8,448件を上限とする。既存phase event上限8,192には通常callbackと追跡対象cleanupを合算し、FileObject generation/proofSequence/counterのincrementはcheckedとする。いずれかの上限・overflowは`F005_ETW_WRITE_COMPLETION_DRAIN_BUFFER_LIMIT`で停止し、無関係cleanup ignoreは上限へ算入しない。

### 3. replay chainとsemantic適用の分離

queue replayは`appliedCursor`から開始する。pending batch全件について、共通`proofSequence`順、各proofの`generationBefore`とshadow cursor、`generationAfter`、retained generation handle identity、producer retained process、checked容量、notice相関をshadow stateへdry-runする。proofの欠落、重複、順序逆転、generation gap、seal exact generation差、同じFileObject generationでのidentity/path差は`F005_ETW_WRITE_COMPLETION_DRAIN_BINDING_MISMATCH`で停止する。全件dry-run成功後だけ、applied cursor、semantic `filesByObject`/`filesByPath`、notice、Observation、allocated/peak/freeを一括commitする。後半proofまたは容量計算が失敗した場合も、先行eventを含む実stateは一切変更しない。applied後もretired generationとhandleはseal/phase releaseまでimmutableに保持し、同じ数値のFileObject再利用は別generationとして区別する。

replay完了後もledger admission headとapplied cursor、全queued proof末尾の一致をfinal admission writer区間で確認する。final writer取得前の差だけは新callback raceとしてstate無変更で再fenceする。writer取得後に通常/cleanup counterが安定しqueueが空なのにcursor/headが不一致なら内部proof破損として`BINDING_MISMATCH`へfail-closedする。`TryAuthorizeWriteCompletionDrainEventLocked`、`ApplyCallbackSnapshotLocked`、`CompleteWrite`、`EndPhase`の全completion-drain再照合から`TryInspect(path)`とsemantic `filesByObject`参照を除き、retained current/directory/generation handle identity、seal時lease FileObject exact generation、ledger applied cursor/admission headだけを使う。Cleanupでseal generationがretiredでも、同generationのimmutable identity/pathとhandleが一致し後続再利用が別generationなら正当とする。phase終了時はqueue解決、通常callbackとcleanup双方のrelevant/accounted安定、ledger cursor/head一致を確認してからhandleとledgerを解放する。

固定評価順は、state/epoch/path kind → proof delivery/generation/binding（`BINDING_MISMATCH`）→ retained handle safety/identity（`EVENT_IDENTITY_FAILED`）→ producer process → checked capacity/noticeとする。複数不一致時もこの純粋ruleの先行codeだけを返す。

### 4. 外部契約

外部へ伝播する固定codeはCHG-F005-037の21件を変更しない。retained identity異常は既存`EVENT_IDENTITY_FAILED`、proof chain異常は既存`BINDING_MISMATCH`へ分類する。private IPC、TypeScript順序、notice schema、Job/producer tuple、容量actual計算、candidate保存、公開条件、`public/`、`data/`は変更しない。raw path、FileObject、generation、identity、handle値はjournal annotation、reply、error messageへ出さない。

## 試験方針

- retained current/directory handleのopen flags（directoryは`BACKUP_SEMANTICS`必須）、identity一致、reparse/hardlink拒否、最大256、prepare失敗・poison・release・close各disposeをnative executable testで固定する。
- 初回prepareの`admission writer → gate`線形化、read token取得済みcallbackのbaseline所属、writer待機後callbackのproof所属、baseline generation `0/1`、`proofSequence/admissionHead/appliedCursor = 0`を固定する。sealed-current before=after、sealed-parent unbound before=after、other-bound bootstrap/rebind、rename、write/setinfo、delete→Cleanup、Cleanup→delete、同種duplicate、後続FileObject再利用についてgeneration/state遷移をproduction共有ruleで全分岐検査する。

- ledger/proof合計/queue/generation handle各8,192とlive handle総数8,448の境界、generation/proofSequence/counter checked overflowを固定する。
- callback順7種と、rename後path欠落、replay前後のsemantic `filesByObject`変化を投入し、lookup/replay/CompleteWrite/EndPhaseが`TryInspect(path)`とsemantic `filesByObject`を参照せず同じObservation/actualとなることを確認する。
- proof欠落、重複、逆順、generation gap、identity/path差、queue先頭cursor差、replay末尾/head差を1件ずつ変化させ、先行失敗を`BINDING_MISMATCH`へ固定する。
