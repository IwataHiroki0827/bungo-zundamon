# CHG-F005-041 exact late current SetInfoのcompleted-write認可引き渡し

## 変更理由

commit `c58792691b422dd4682d1fe04b2bc1cb50a35691`のActions run `31205281066`は、T-070 production pipelineの`wav-validated`後に`F005_ETW_WRITE_COMPLETION_DRAIN_LATE_DIAG_SETINFO_CURRENT_PATH`で安全停止した。対象はcompleted-retained sealのcurrent pathで、seal lease FileObject、exact generation、current identity/pathの`ProofCandidate`を通過している。

現行の認可chainはcompletion drainを`TryAuthorizeCompletedSystemSetInfoLocked`より先に評価する。後者は既存のcompleted-write契約として、System PID 0/4の`setinfo`、同一phase、予約QPC後、完了2秒window、FileObject binding、current existence、identity一致をすべて再検査してから認可する。しかし、現在はcompletion drainのexact late拒否により後者へ到達できない。新しい認可規則は追加せず、対象bucketだけを既存契約へ引き渡す。

## 予定変更

### 1. handoffの完全条件

completion drainの`epoch.Length == 0`経路で、次の全条件を満す場合だけ、throwに代えてcompleted-write専用handoffを返す。

- broad candidate、epoch 0、exact late `ProofCandidate`の既存条件が成立する。
- `lateCandidates.Length == 1`である。
- 決定的集約codeがexact `F005_ETW_WRITE_COMPLETION_DRAIN_LATE_DIAG_SETINFO_CURRENT_PATH`である。
- `completedWrites[normalized]`が存在し、worker PID、process sequence、phase instance、reserved QPC、identityが対象sealと完全一致する。

handoffは通常の`completionDrainSeal`とは別のopaque contextとして対象sealを保持し、同一`gate`内で照合する。候補0/複数、write、parent、他の不一致軸、`MIXED_CAUSES`、genericは従来codeで同じ位置からthrowする。completed record欠落またはseal tuple差は既存`F005_ETW_WRITE_COMPLETION_DRAIN_STATE_CHANGED`で停止する。

### 2. completed-write認可への専用分岐

`ObserveEtw`はhandoffを受けた場合、reserved SetInfoや他の後段認可へfall-throughせず、直ちに既存`TryAuthorizeCompletedSystemSetInfoLocked`を評価する。完了契約がPASSした場合だけ、保存済みworker PID/process sequenceへ再結合し、既存のcurrent identity再検査とnormal callback適用へ進む。

completed-write認可が固定拒否した場合はその既存`ETW_COMPLETED_WRITE_REJOIN_*`でpoisonし、他の認可を試さずreturnする。専用分岐到達後にcompleted recordが消失した場合は`STATE_CHANGED`で停止する。

認可PASS後のnormal callbackには`completionDrainSeal == null`で渡し、handoff sealを`AdmitCallbackProofLocked`のseal引数へ渡さない。既存normal callback契約どおり、ledgerがある場合の`OtherBound` proofは`SealSequence == null`で1件生成・適用する。一方、handoff sealに結び付くsealed proof、sealed recheck/reorder/replay、seal `EventCount`更新は0件とする。late timestampをcompletion drain epochとして再検査せず、既存completed-write認可と既存normal callbackの組合せだけを使用する。

### 3. 認可集合の限定

追加認可集合は「completion drain exact late current SetInfo」と「既存completed-write認可の完全条件」の共通部分だけである。後者の2秒window、binding、current existence、identity再検査を緩和しない。completion drainのepoch内処理、parent event、write、複数candidate、他の診断code、seal/lease/ledger/queue/semantic/capacity/notice/Observation、外部35 code、IPC、raw値非公開、candidate/Pages条件は変更しない。

## 影響範囲

`tm.json`の`DES-F005-006`/`DES-F005-012`から、`REQ-F005-012`、`REQ-F005-013`、`FUN-F005-017`、`FUN-F005-047`、`UT-F005-017`、`UT-F005-047`、`IT-F005-005`、`QT-F005-008`、`QT-F005-009`、`T-070`、`T-114`、`T-115`を影響対象とする。

## 試験方針

- handoff純粋規則のall-true、candidate count 0/1/2、write/setinfo、current/parent、他bucket、MIXED、genericを固定する。
- completed recordとsealのworker PID、process sequence、phase instance、reserved QPC、identity各単独差を`STATE_CHANGED`とする。
- handoffがreserved/known-directory/他rejoinより先に専用completed-write認可だけを呼び、拒否後にfall-throughしない構造を固定する。
- handoffは通常の`completionDrainSeal`と別out/tri-stateであり、PASS後は通常`OtherBound` proofを`SealSequence == null`で1件生成する一方、handoff sealのsealed proof生成0、sealed recheck/reorder/replay呼出し0、seal `EventCount`変化0であることを固定する。
- 既存completed-write認可の全trueと、authorization、PID、event、FileObject 0、phase、予約QPC、2秒window、binding、current existence、identity各falseを再実行する。
- 引き渡し前後の認可失敗でseal/lease/ledger/queue/semantic/capacity/notice/Observationが無変更であること、外部35 code・pin・公開treeが許可なく変更されないことを確認する。
- native rules、関連Vitest、typecheck、ESLint、trace_check、再現build 2回、独立受入、`public/`・`data/`差分0件を確認する。
- 同一source SHAのhosted productionで、completed-write認可PASSによる先行bucket通過または既存の固定拒否stageを証拠化する。

## 承認

既存の二重認可契約の交差だけを引き渡すdesign変更であり、要求承認ゲートは設けない。独立設計レビュー、実装、影響試験、hosted再観測まで`in-review`を維持する。

独立設計レビューは初回H0/M1/L0、再レビューH0/M1/L0の指摘を反映した。handoff sealと通常`completionDrainSeal`を分離し、既存normal `OtherBound` proofだけを維持する契約へ一意化した最終再レビューはH0/M0/L0でPASSした。
