# 関数設計書 F006（中島敦3作品追加）

## 0. 再利用方針

F006は「新規作者1人・3作品追加」という構造がF003と同型であり、F005が導入したETW常時監視・native guard機構（`f005-native-guard.ts`、`native/f005-guard/`）は使わない。CHG-F005-072以降にF005自身が確立した「phase前後の実測差分による事後検証」と、実際のv0.5.0公開（CHG-F005-083）で採用された汎用release経路は、値がfeatureに依存しない汎用実装であるため直接再利用する。

以降の各`FUN-F006-*`は、DESごとの追跡用論理IDである。多くは実装として新規コードを書かず、既存関数をそのまま呼び出す（本文に既存関数名を明記する）。値（authorId・workId・release commit・catalog SHA・既存作者画像枚数等）がfeatureごとに異なるために既存モジュールを直接呼べないもの（baseline pin・author/work registry・catalog統合・route導出・artwork provenance、計7件）だけを新規コードとして定義する。実装フェーズでは、再利用する既存関数のJSDocへ`@des DES-F006-xxx @fun FUN-F006-xxx`を追記する（F003〜F005で確立済みの複数タグ蓄積規約、例: `batch-candidate.ts`の関数群）。

## 1. 候補・baseline・作者identity

### FUN-F006-001: F006承認候補registryのvalidate・atomic書込み・manifest生成 [DES-F006-001]

新規コードなし。既存`validateBatchCandidateRegistry`・`writeBatchCandidateRegistryAtomic`（`src/content/batch-candidate.ts`）でF006候補のexact keys・author/work/approvalBinding・重複・URL/path安全性を検証し、expected old SHA・canonical JSON・temporary file・atomic rename・post-read hashで`content/batch-candidates.json`へ追記する。既存`loadAndVerifyClosedApproval`で`docs/evidence/requirements/F006-approval-binding.json`のqueue item hashとApproved SRS-F006/QT-F006実体を照合した`VerifiedClosedApproval`を得て、既存`selectApprovedBatchCandidateAndCreateTemplate`（または`createBatchManifestFromApprovedContext`）で一致した1候補だけを`content/batches/F006/batch.json`の`draft`へmaterializeする。F006向けの新規application exportやID分岐は作らない。異常は既存code（`CANDIDATE_REGISTRY_INVALID`等）をそのまま用いる。

### FUN-F006-002: loadPublishedV050Baseline(workspace, options?) -> Promise<PublishedV050Baseline> [DES-F006-002]

### FUN-F006-003: isMintedPublishedV050Baseline(value) -> value is PublishedV050Baseline [DES-F006-002]

`f004-baseline.ts`の`isMintedPublishedV030Baseline`と同型のbrand検査関数。F004の実装が`load`関数と`isMinted`brand検査だけを提供し、tree/catalog/dist不一致の実体比較を`load`内部で完結させている構造をそのまま踏襲し、別立ての`verifyInvariant`関数は新設しない。work preview・統合tree・distの各段階で同一固定bundleを`isMintedPublishedV050Baseline`で再検証してから使う。

### FUN-F006-004: defineF006AuthorAndWorkRegistry() -> F006WorkRegistry [DES-F006-003]

`f006-baseline.ts`または新規`f006-source.ts`のmodule-private定数として、`authorId=000119, originalName=中島敦, name=なかじまあつし, slug=nakajima-atsushi`と、`000624`（山月記, order 1）→`000621`（名人伝, order 2）→`001738`（弟子, order 3）のexact work tupleを保持する。既存`BatchAuthor`のcanonical fieldsから`identitySha256`を再計算し、F006候補registry（FUN-F006-001）とcanonical candidateのauthor/work記述がこのregistryと一致することを検証する。既存`verifyExistingAuthorIdentity`（`batch-candidate.ts`）へこのregistryを渡し、DES-F006-002のbaseline join 0件・他4作者との非衝突を検証する。3作品全てのauthorIdが`000119`の場合だけ`authorMode=introduce`を許可する。汎用CAS遷移（`pending → extracted → reviewed → budget-approved → voiced`）は既存`transitionWorkState`（`batch.ts`）をそのまま用いる。不一致は`F006_REGISTRY_MISMATCH`。

## 2. 権利・原典・抽出・レビュー

### FUN-F006-007: F006独立二重判定・裁定・回復 [DES-F006-006]

## 3. 音声・容量・受入

### FUN-F006-009: F006差分音声生成・容量forecast・write健全性事後検証 [DES-F006-008]

新規コードなし。単一候補安全性・差分音声生成は既存`planVoiceDiff`・`authorizeVoiceDiffPlan`・`generateVoiceDiff`・`verifyVoiceCompleteness`（`src/voice/generation.ts`）をそのまま用いる。固定VOICEVOX tuple（ENGINE `0.25.2`、speaker UUID、style ID `3`、style名`ノーマル`、24 kHz/mono/16 bit PCM）はF002以来の既存configをF006向けにcanonical複製する。容量forecastは既存`forecastCapacity`・`measureGitRepository`・`verifyActualCapacity`（`src/voice/budget.ts`、ETWに依存しない汎用実装）を用い、追加WAV・Pages artifact・source repository・単一Git object・作業ドライブの各区分をbyte単位で判定する。

書込み健全性（宣言外pathの新規出現・変更・消失が0件であること）は、SRS §3.1が明示するとおりCHG-F005-072で確立した事後検証方式をそのまま継続利用する。既存`scanF005Workspace`でphase開始時にbaseline snapshotを取り（追跡root `content`/`data`/`public`、`F005_TRACKED_ROOTS`の値はfeature非依存でそのまま適用できる）、既存`foldF005Declarations`で宣言済みmutationをsequence順に畳み込み、phase完了後に既存`verifyF005Postconditions`で実測差分とexact一致することを検証する。一時書込みは既存`writeF005TemporaryFile`（`f005-postcondition-write.ts`、排他作成+fsync+読み戻しSHA照合）で行う。native guardやETW常時監視は新設しない。いずれか不成立ならfail-closedとし、raw pathを出さない固定codeで停止する。

### FUN-F006-010: F006作品単位atomic受入・回復 [DES-F006-009]

新規コードなし。山月記→名人伝→弟子の順にだけ`pending → extracted → reviewed → budget-approved → voiced → accepted`へ進める。既存`promoteVerifiedWorkArtifacts`（`src/content/batch-acceptance.ts`）がcaller作成の`pass`値を信用せず、canonical allowlist pathからprimary/secondary/adjudication、safety、音声、容量、FUN-F006-002のbaseline原artifactを再読込・再計算したbranded evidenceだけを使う。exclusive lock・expected manifest/tree hash・random staging・journal・file sync・atomic rename・postwrite hash・bounded retryは既存契約をそのまま継承する。process停止後は既存`recoverBatchSourceArtifactPromotion`（`batch-production.ts`）および`promoteVerifiedWorkArtifacts`内部journalから旧版または完成新版へ決定的に回復し、第三者変更を上書きしない。manifest書込みは既存`writeBatchManifestAtomic`（`batch.ts`）を用いる。
