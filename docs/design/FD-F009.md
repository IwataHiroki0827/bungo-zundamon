- 承認候補registry・汎用CAS・4ゲート参照（`src/content/batch.ts`、`batch-candidate.ts`）

## 3. 原典・抽出・レビュー

### DES-F009-004: 権利適格性と原典固定 [REQ-F009-005][REQ-F009-006]

選定時とpredeploy時に、既存`ProductionAozoraTransport`（F002〜F008が使用するHTTPS exact allowlist・DNS public IP確認・接続IP pin・redirect/proxy/retry禁止のtransport）だけを用いて公式拡充CSV・作家ページ・図書カードを取得し、人物/作品著作権なし、役割=著者、翻訳者なし、公開中、新字新仮名、author/work/URL一致を確認する。VOICEVOX・ずんだもんの各利用規約へ無料・広告なし・課金なし・スポンサーなし・非公式の用途分類と必須creditを適用し、`decision: allow`だけを取得日時・URL・raw SHA・接続証跡付きでrelease commit/runへ結合する。差分・未判定・transport異常はfail-closedとする。

XHTML（`2381_13352.html`／`46694_27682.html`／`2380_13349.html`）はexact URL、raw bytes、charset、本文selector、取得日時、SHA-256、底本、入力者、校正者、更新日を作品別`SourceRecordV2`相当へ固定する（`proofreader`はnon-null値のみを使用）。predeploy観測はrelease commitと結合し、選定時との差分・期限切れ・欠落を停止条件とする。DOMAIN-F009.mdで実際に取得済みのraw SHA-256（瓶詰地獄`40131af4befaf98e729089f8103805f0001d9c5685977ea198642444d2b3b62d`・きのこ会議`9557eae04d5ba3a7b681f21cfd6157c32c001a57d6a6b8544b2e8290d7462f81`・死後の恋`ea4317c3ed579d0c4e95bc07372bda39e54991c458e95a7dcb8d375882ceec70`）は選定時snapshotの参照値とし、公開直前の再取得時に同一かどうかを実測で確認する（一致を前提にせず改めて検証する）。

### DES-F009-005: 未定義entity・gaiji検出（常時有効）と決定的抽出 [REQ-F009-007]

原典rawは変更せず、raw SHA-256を先に検証する。既存の未定義named entity検出手順（`preflightF00NXhtml`/`normalizeF00NAozoraXhtmlEntities`と同型の標準5種entity allowlist検査）を選定時と公開直前の独立snapshotで実行し、対象3作品に未定義entityが0件であることを確認する（DOMAIN-F009.md §5で実測確認済み）。

**gaiji要素の検出は本DESの新規論点である**。DOMAIN-F009.md §5のとおり瓶詰地獄・死後の恋の地の文には`<img class="gaiji">`要素が実在する（候補内には0件該当を選定時に確認済み）。F005〜F008の採用9作品ではこの種の要素が一度も検出されなかったため、既存実装には「XHTML中のgaiji img要素の出現位置」と「抽出済み候補のtoken range」を突き合わせる専用ロジックが存在しない。F009は新規に`detectF009GaijiElements(rawText)`（`<img\b[^>]*class="gaiji"[^>]*>`相当の要素を走査し、byte offset集合を返す）と`verifyNoGaijiWithinCandidates(candidateSet, gaijiOffsets)`を`f009-source.ts`へ実装し、選定時と公開直前の独立snapshotの両方で、gaiji出現位置と候補の`rawTokenRange`の重なりが0件であることを機械的に検証する。1件でも重なりが検出された場合はfail-closedで当該作品を`pending`に留める。既存の`normalizeSpeechText`（`processing.ts`）が持つ`/[〓※�]/u`検査（speechText確定時の残存gaiji検出）はfeature非依存のまま無変更で適用され続け、F009はこの経路にも条件分岐によるスキップを追加しない。

固定原典のexact XHTML 1.1外部DOCTYPE宣言だけをnetwork/filesystem resolverなしで許し、internal subset、他DOCTYPE、ENTITY、XInclude、外部schema/stylesheetをアクセス前に拒否する。深さ・node・属性・text上限内だけを解析し、候補ID・順序・表示文を決定的に生成する。同じ入力2回で候補集合のcanonical hashが一致しない場合は非決定的として停止する。

### DES-F009-006: 独立二重判定 [REQ-F009-008]

全候補をprimary/secondaryが互いの結果を見ずに判定する。既存`editorial-independent.ts`（F002〜F008が使用する汎用モジュール）の`registerEditorialAuthorizations`・`sealAndValidateEditorialJudgmentSet`・`reconcileIndependentJudgments`・`verifyEditorialCompleteness`・`loadAndVerifyEditorialJudgmentSets`をそのまま用い、`candidateSetSha256/policySha256/promptSha256/toolSha256/nonce`を含む一回限りのauthorizationで判定を封印する。不一致digestが確定した場合だけ第三裁定（adjudicator）authorizationを発行し、それ以前の裁定を拒否する。最終`pending: 0`まで音声stageへ渡さない。**死後の恋の長大候補（DES-F009-005の分割対象）は分割後の各piece candidateが独立したcandidateIdを持つため、分割前の1件ではなく分割後の複数candidateそれぞれに対して独立二重判定を実施する（下記8節）。** 合計かぎ括弧候補51件・発話文字概算3,714文字はF006（62件・2,412文字）と同程度で、F007（108件・12,912文字）・F008（106件・11,893文字）より判定作業量が少ない。

### DES-F009-007: 読み上げ補正 [REQ-F009-009]

display textは原文のまま保持し、旧語・固有名・ロシア語由来の外来語（ペトログラード・ソヴィエト等、死後の恋）の読み補正を既存`applySpeechRevisions`（`src/content/f003-reuse.ts`）のbefore/after/reason/revision/hash chainへ記録する。瓶詰地獄の往復書簡体特有の文語表現、きのこ会議の擬人化・児童向け語彙、死後の恋の大正〜昭和初期口語表現・革命関連固有名はVOICEVOX実測に基づき個別に補正候補を作成する。候補の余分・欠落・重複・pendingを0としたreconciliation digestを後続stageへ固定する。

### DES-F009-008: 単一候補安全性・差分音声・容量事後検証 [REQ-F009-011][REQ-F009-012]

書込み健全性（宣言外pathの新規出現・変更・消失が0件であること）は、SRS §3.1が明示するとおりCHG-F005-072で確立した事後検証方式をそのまま継続利用する。既存`scanF005Workspace`でphase開始時にbaseline snapshotを取り、既存`foldF005Declarations`で宣言済みmutationをsequence順に畳み込み、phase完了後に既存`verifyF005Postconditions`で実測差分とexact一致することを検証する。一時書込みは既存`writeF005TemporaryFile`で行う。native guardやETW常時監視は新設しない。いずれか不成立ならfail-closedとし、raw pathを出さない固定codeで停止する。

### DES-F009-009: 作品単位atomic受入 [REQ-F009-013]

瓶詰地獄→きのこ会議→死後の恋の順にだけ`pending → extracted → reviewed → budget-approved → voiced → accepted`へ進める。受入は既存`promoteVerifiedWorkArtifacts`（`src/content/batch-acceptance.ts`）をそのまま用い、caller作成の`pass`値を信用せず、canonical allowlist pathからprimary/secondary/adjudication、safety、音声、容量、DES-F009-002のbaseline原artifactを再読込・再計算したbranded evidenceだけを使う。work artifactのcanonical保存先・作業staging・exclusive lock・expected manifest/tree hash・random staging・journal・file sync・atomic rename・postwrite hash・bounded retryは既存契約をそのまま継承する。process停止後は既存journalベースの回復から旧版または完成新版へ決定的に回復し、第三者変更を上書きしない。F006〜F008実装で判明した「間接ハッシュ規約と`promoteVerifiedWorkArtifacts`の直接evidence要求が噛み合わない」問題が同型で発生する見込みが高く、F006〜F008同様の薄い受入ラッパー（`src/content/f009-acceptance.ts`）を新設する前提とする（詳細はDD-F009.mdで確定する）。

## 8. 長大候補への実対応

### DES-F009-015: F007/F008由来の長大候補分割手法の実発動 [REQ-F009-019]

F007で確立しF008で踏襲した「単一発話が閾値600文字（実測失敗境界1,335文字の2倍以上の安全マージン）を超える場合、句点『。』の文境界でのみ複数の連続candidateへ分割する」手法（`f008-source.ts`の`splitOverlongF008Candidates`）を、`f009-source.ts`（DES-F009-004/005で新設）へ同一閾値・同一アルゴリズムでそのまま複製する。

DOMAIN-F009.md §3.1が指摘するとおり死後の恋の1候補は選定時実測で正規化前1,748文字であり、600文字閾値を明確に超過している。F007では防御的に実装されたが実データでは発動せず、F008でも同様に発動しなかったのに対し、**F009は選定時点で既に発動が見込まれる最初の実ケースである**。これに伴い、設計上以下を明示する。

- 分割後の各piece candidateは独立した`candidateId`（displayText/speechTextのhashから導出）を持ち、`sourceAnchor`/`rawTokenRange`/`rawSourceSha256`は分割元と同一を維持する。
- 分割後の複数candidateはDES-F009-006の独立二重判定を**piece単位で個別に**実施する（分割前の1候補をまとめて1回判定するのではなく、分割後生成された各candidateをそれぞれ独立にprimary/secondaryへ提示する）。
- 分割後の各piece candidateはDES-F009-008のVOICEVOX synthesisも**piece単位で個別に**実行し、各pieceが単一候補の500 code point・120,000 ms上限を満たすことを個別に確認する。
- `scripts/f009-prepare-editorial.ts`の`speechCorrections`適用ロジックは、F007/F008と同様に分割後の複数candidateが同一`sourceAnchor`を共有するケースに対応させ、「宣言された各補正は合計ちょうど1回だけ適用される」不変条件を検証する。
- 分割処理自体の決定性（同一入力2回で分割結果のcanonical hashが一致すること）を実装フェーズのUT/ITで別途検証する。この検証はF007/F008でも設計上要求されていたが、実候補が存在しなかったため分割ロジックの多くの分岐（複数piece生成・piece数2以上のorder再採番等）が実データで一度も通っていない。F009は分割ロジックのこれらの分岐が初めて実データで実行される機会であるため、実装フェーズのレビュー・テスト計画に「分割後candidateの個別二重判定」「分割後candidateの個別音声化」を明示的なタスクとして含める。

共有汎用音声モジュール（`src/voice/generation.ts`・`src/voice/client.ts`・`src/content/processing.ts`・`src/content/batch-production.ts`）は変更しない。
