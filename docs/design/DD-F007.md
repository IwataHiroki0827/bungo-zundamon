# 関数設計書 F007（森鴎外3作品追加）

## 0. 再利用方針

F007は「新規作者1人・3作品追加」という構造がF006と同型であり、F005が導入したETW常時監視・native guard機構は使わない。CHG-F005-072以降に確立した「phase前後の実測差分による事後検証」と、F001〜F006実績の汎用release経路は、値がfeatureに依存しない汎用実装であるため直接再利用する。

以降の各`FUN-F007-*`は、DESごとの追跡用論理IDである。多くは実装として新規コードを書かず、既存関数をそのまま呼び出す（本文に既存関数名を明記する）。値（authorId・workId・release commit・catalog SHA・既存作者画像枚数・舞姫notice registry等）がfeatureごとに異なるために既存モジュールを直接呼べないもの（baseline pin・author/work registry・catalog統合・route導出・artwork provenance・薄い受入ラッパー、計7件）だけを新規コードとして定義する。実装フェーズでは、再利用する既存関数のJSDocへ`@des DES-F007-xxx @fun FUN-F007-xxx`を追記する。

### FUN-F007-010: F007作品単位atomic受入・回復 [DES-F007-009]

F006実装で確認済みの通り、汎用`promoteVerifiedWorkArtifacts`の`assertInputs`は`voiced`stageの`outputHashes`に直接evidence値を要求するが、F006が確立した「間接ハッシュ規約」（`voiceEvidenceRef`ファイルのSHA-256だけを格納する方式）はF007でも同一パターンで踏襲する予定であり、両者は同じ理由で直接には噛み合わない見込みが高い。F006と同じパターンで、**F007専用の薄いacceptanceラッパー`src/content/f007-acceptance.ts`を新設する**（既存`promoteVerifiedWorkArtifacts`・`batch-production.ts`の`recoverBatchSourceArtifactPromotion`・`writeBatchManifestAtomic`は変更せずそのまま呼ぶ薄い橋渡し層とする）。実装フェーズの最初のwork（舞姫）着手時に、F006と同じ噛み合わせ問題が実際に発生するかを実装検証したうえで確定する（発生しない場合は`f006-acceptance.ts`型のラッパーを作らず汎用関数を直接呼ぶ、より単純な設計へ切り替えてよい）。
